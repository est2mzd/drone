# D01 保存動画と映像入力の意味

図の対応：DFD（Data Flow Diagram、データの流れを示す図）・境界図の「保存動画」。接続は **O02 → A03**。O02側で保存された動画を、A03の読込・時刻付与へ渡す境界である。

本章の対象は、保存済みの動画をPC上で処理する現行のオフライン運用。SLAM（Simultaneous Localization and Mapping、自己位置推定と地図作成の同時実行）本体が直接機体の通信を受ける仕組みではない。収録・通信の詳細はO02へ譲る。

## 保存ファイルを入力にする目的

保存動画を使うと、記録済みの映像を入力として繰り返し処理できる。読み出す入力を固定できる一方、並行処理を含むSLAMの全出力が毎回完全一致することまで示すものではない。

リポジトリ直下のREADMEは、保存した`.mp4`をPCで追跡する運用を説明している。`run.sh`は動画名を受け取り、語彙・設定・動画・出力先の順で`offline_mono`へ引数を渡す。ここでD01が表すものは、まだ特徴点や地図点ではなく、後から画像を取り出すための記録である。

入力側には動画の場所を示す文字列があり、読込側はそこから画像を順に得る。校正と特徴の辞書は別の入力であり、動画に含まれていると仮定しない。三入力の関係はA01を参照する。

## ファイル・圧縮映像・復号画像の三段階

```text
O02側で保存したファイル
    ↓ パス文字列をVideoCaptureへ渡す
OpenCVが入力を開き、次の画像を取得・復号する
    ↓ read(frame)が成功
cv::Matの画素配列 → A03で時刻を付与 → TrackMonocular
```

OpenCV（Open Source Computer Vision Library）は画像・動画を扱うライブラリである。ここでは`VideoCapture`がファイル等から画像を取り出す役割を持ち、`cv::Mat`が受け取った画像の配列を表す。

| 段階 | この段階で扱うもの |
| --- | --- |
| 保存ファイル | ファイル名・パスで指定する記録。拡張子は名前の一部であり、中身を検査した結果ではない |
| 圧縮された映像データ | 画像を符号化して保存する表現。圧縮方式を扱うコーデックと、データを格納する形式は別の概念 |
| 復号後の画像 | 復号器が得た画素値の配列。特徴抽出などの画像処理へ渡せる形 |

したがって、圧縮された動画ファイルのバイト列を、そのまま画素の縦横配列として読めば画像になるわけではない。現行の`TrackMonocular`へ渡すのは、`read`で得た`frame`であり、動画ファイルそのものではない。

READMEの運用は`.mp4`だが、wrapperは拡張子・コーデック・ファイル種別を独自に検査せず、`video_path`という文字列を`VideoCapture`へ渡す。OpenCVの文字列入力は他の入力形態も扱い得るため、「実装がmp4だけを許可している」という契約とは区別する。

## 復号画像を最小の式で表す

説明のため、各成分が符号なし8bitで、画像間の高さ・幅・チャネル数が一定の場合を考える。

\[
I_k\in\{0,1,\ldots,255\}^{H\times W\times C},\qquad k=0,1,\ldots,N-1.
\]

| 記号 | 型・単位・前提 |
| --- | --- |
| \(I_k\) | k番目に読込成功した画像の画素配列。各成分は0〜255の整数のコード値であり、物理的な光量の単位は与えていない |
| \(k\) | 0から始まる読込成功画像の順番。整数で単位なし。撮像時刻や機体側の画像番号ではない |
| \(N\) | 最初に`read`がfalseを返すまでに読込成功した画像数を表す非負整数。元の収録枚数を保証する値ではない |
| \(H,W\) | 正の整数で、高さと幅の画素数。この例では全画像で一定 |
| \(C\) | 正の整数のチャネル数。例えばカラーの3成分やグレーの1成分。空間の三次元座標ではない |

縦横の添字は画像中の行・列を指し、世界座標やカメラの三次元位置はこの式に含まない。画像が一枚も得られなければ`N=0`で列は空となり、`k`に対応する画像はない。式は配列の論理的な形を表し、`cv::Mat`の行間隔などの実メモリ配置を規定しない。

例えば`H=720,W=1280,C=3`なら、一枚の画像には論理上`720×1280×3=2,764,800`個の成分がある。これは圧縮ファイルのバイト数ではない。3チャネルという数だけで色の並び順まで確定することもできない。

`cv::Mat`自体は複数の要素型・チャネル数を扱う一般の配列である。本章の8bit例は実物動画の型・解像度を測定した結果ではなく、wrapperにもそれらを検査する処理はない。寸法・色順と校正の整合はD03、後続のグレー化はA04を参照する。

## 開けたことと、最後まで使えることは別の判断

| 現行コードの段階 | 分かること | これだけでは分からないこと |
| --- | --- | --- |
| `isOpened()`がtrue | 入力を開く初期化が成功した | 全画像の復号可能性、欠落の有無、画質、撮像時刻の正しさ |
| `read(frame)`がtrue | 今回の画像取得・復号が成功した | 次も読めること、特徴が十分あること、追跡成功 |
| `TrackMonocular`へ渡す | 取得画像と生成時刻を本体へ入力した | 初期化や追跡が成立したこと、地図の正確さ |

`isOpened()`がfalseなら、このwrapperは入力名を含むログを出して終了する。開けた後は`read`の成功中だけ処理し、falseでループを抜ける。ファイル終端と途中の取得失敗をこのループだけで分類していない点はA02で扱った。

例えば入力を開けた後、画像3枚の取得が成功し、4回目の`read`がfalseなら、SLAMへ渡した画像は3枚となる。これだけでは、正常に3枚で終わる記録だったのか、途中に読めない箇所があったのかは確定しない。

復号成功は、ぼけ・低コントラスト・圧縮による変化がないという画質検査ではない。現在のwrapperは画質の合否を検査してから入力する構造ではなく、追跡側が得られた特徴・対応で判断する。

また、画素配列だけでは撮影された時刻は分からない。現行wrapperは画像ごとの撮像時刻を取り出す代わりに、読込番号と採用フレームレートから時刻を構成する。計算はA03、FPS（Frames Per Second、毎秒の画像数）の意味はD02で扱う。

## 理解確認

1. `TrackMonocular`が受け取るのは、圧縮ファイルのバイト列か、復号後の画像か。
2. `isOpened()`がtrueなら、最後まで追跡できると分かるか。
3. `I_k`の添字kは、撮影した実時刻を表すか。

答えの要点：復号後の画像／開く初期化の成功であり、復号・追跡の成功は別／読込順の番号であり、時刻は別に与える。
