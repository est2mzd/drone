# D08 各画像の姿勢と状態

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「各画像の姿勢・状態」。接続は **P01/A13 → D13、次画像予測**。純単眼の通常地図構築モードで、一枚の画像を処理した後に得る情報を扱う。

## 姿勢値と処理状態を分けて読む

姿勢は「地図に対してカメラがどの向き・位置関係にあるか」を表す。一方、追跡状態は「初期化前か、追跡を受理したか、復帰を試しているか」などの処理段階を表す。数値の姿勢を持っているだけで、追跡が成立したとは限らない。

入力はD05/D06の画像時刻付きFrameと、追跡に使う地図・過去の観測である。Trackingがそれらから姿勢仮説を設定し、対応の確認や最適化、成立判定を行う。結果は呼出し元へ返す姿勢値、別途取得する追跡状態、条件付きで追加する内部履歴などに分かれる。

| 情報 | 保持・取得先 | 表すことと限界 |
| --- | --- | --- |
| 姿勢値`Tcw` | `Frame::GetPose()`、`System::TrackMonocular()`の戻り値 | 世界→カメラの変換値。戻り値だけには成功フラグを含まない |
| 姿勢設定フラグ | Frameの`mbHasPose`、`HasPose()` | `SetPose`で値を設定したこと。追跡の最終受理とは別 |
| 追跡状態 | Trackingの`mState`、Systemの`GetTrackingState()` | 処理段階・成立判定を表す整数の列挙値。位置や姿勢ではない |

Frameの`SetPose`は、姿勢値と派生行列を更新し、`mbHasPose`と`mbIsSet`をtrueにする。A09の参照KF追跡では、最適化・成否評価より前に初期姿勢も設定する。従って、`HasPose()==true`を`state==OK`へ読み替えてはならない。KFはKeyFrame（地図の代表となるキーフレーム）の略である。

## Tcwはカメラ位置そのものではない

姿勢`Tcw`は、回転と並進を保持する`Sophus::SE3f`型で返る。その回転・並進成分とカメラ中心の関係を、次のように整理する。

\[
X_c=R_{cw}X_w+t_{cw},\qquad
C_w=-R_{cw}^{\mathsf T}t_{cw}.
\]

| 記号 | 型・座標系・単位・前提 |
| --- | --- |
| \(T_{cw}\) | 世界wからカメラcへの剛体変換。下添字cwは変換先c・変換元wの順 |
| \(X_w,X_c\) | 同じ三次元点を世界座標、カメラ座標で表した長さ3の実数列ベクトル |
| \(R_{cw}\) | 3×3の実回転行列。正規直交かつ行列式＋1、成分は無次元 |
| \(t_{cw}\) | 世界→カメラ変換の並進を表す長さ3の実数列ベクトル。カメラ座標側の成分 |
| \(C_w\) | カメラ原点を世界座標で表した長さ3の実数列ベクトル。これが世界座標でのカメラ中心 |
| 上付き\(\mathsf T\) | 転置。回転では転置が逆行列になることを利用する |

X、t、Cの単位は同じ地図の長さ単位である。純単眼では任意尺度なので、自動的にメートルとはならない。カメラ座標の軸は右・下・前方をそれぞれ正のx・y・z方向とする。世界座標はそのMapの基準であり、新しいMapとの座標関係はA20を参照する。

カメラ原点のカメラ座標は零ベクトルなので、`0 = Rcw Cw + tcw`を解くと上のカメラ中心の式になる。つまり、`Tcw.translation()`をそのまま世界座標のカメラ位置として描くと、向きと符号を取り違える。

例えば回転なし、すなわちRcwが3×3単位行列で、tcwが`(-2,0,0)`の列ベクトルなら、Cwは`(2,0,0)`になる。数値2は仮定した地図単位であり、2mの計測結果ではない。また、この変換を`SetPose`したことだけでは、その仮説が画像に整合して追跡を受理されたことまで証明しない。

## 呼出し元にはどう戻るか

```text
GrabImageMonocular: Frameを構築 → Track() → GetPose()を返す
    ↓
System: Tcwを受け取る → mStateをmTrackingStateへ転記 → Tcwを返す
    ↓
wrapper: 戻り値は保持しない → GetTrackingState()が2なら件数を増やす
```

通常の呼出し完了経路では、Systemは状態用mutexを取得してTracking状態を転記し、`GetTrackingState`もmutex下でその値を返す。姿勢の戻り値と状態値は別の経路であり、返却された姿勢型の中に`HasPose`や`OK`が付属しているわけではない。

| 主な状態値 | 読み方 |
| --- | --- |
| `NO_IMAGES_YET=0`、`NOT_INITIALIZED=1` | 画像未処理段階・初期化未成立段階 |
| `OK=2` | 現行の成立規則で追跡を受理した状態 |
| `RECENTLY_LOST=3` | 一時的に追跡を失い、復帰を試す状態 |
| `LOST=4` | 追跡喪失の確定状態。地図管理によって後続で状態が変わり得る |

これは代表値の意味で、状態遷移全体はA05/A08/A12〜A22を参照する。`OK`は数値精度や実尺度の証明ではない。逆に姿勢仮説が設定済みでも、成否評価で`OK`にならない場合がある。

現行wrapperは`TrackMonocular(frame,timestamp);`と呼ぶだけで、返却Tcwを変数やファイルへ保存しない。別に取得した状態が定数`kTrackingOk=2`と一致した回数を`tracked`へ加える。読込成功画像数の`frame_index`と、このOK件数は別の計数である。

なおSystemには、Shutdown済みなら状態転記より前に既定のSE3値を返す早期経路もある。上の順序は通常完了経路の説明であり、正常なwrapperはShutdown後に画像入力を続けない（A23）。

## 次画像予測と履歴への接続

現在と前画像の姿勢は、条件を満たすと次画像の初期姿勢予測にも使われる。現行の運動モデル更新条件は`bOK`または`RECENTLY_LOST`で、両Frameの姿勢設定も検査する。成功時だけの更新と単純化せず、相対変換の方向や時間間隔の限界はA09へ委ねる。

内部履歴は、全ての画像入力に対して無条件に一行ずつ追加する構造ではない。初期化未成立でのreturnやA18のLOST処理後のreturnは、末尾の履歴追加部に到達しない。例えば最初の画像を初期化候補として保存して戻る場合、入力数は増えても、この姿勢履歴は増えない。

履歴部へ到達しても、状態が`OK`または`RECENTLY_LOST`のときに限って処理する。そこで`isSet()`を検査し、設定済みなら参照KFに対する相対姿勢・参照・時刻を追加し、そうでなければ前の履歴値をコピーする枝がある。返却Tcwを常にそのまま追加する処理でも、常に今回の時刻を追加する処理でもない。詳細はD13で扱う。

終了時の独自姿勢出力も、この内部履歴側を使う。従って、入力画像数、OK件数、履歴要素数、実際の保存行数を同じものとして扱わない。保存形式・選別条件・書込成否はA23とD15へ譲り、本章では実ファイルの行数を測定していない。

## 理解確認

1. `Tcw`の並進は、世界座標でのカメラ中心か。
2. `HasPose()==true`と`state==OK`は同じ意味か。
3. wrapperは何を数え、入力画像数と履歴要素数は常に一致するか。

答えの要点：逆変換で求める別の量／設定済みと受理状態は別／状態2の件数を数え、履歴は条件付きなので一致を保証しない。
