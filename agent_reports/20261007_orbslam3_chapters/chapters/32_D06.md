# D06 Frameと特徴・対応情報

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「Frame：時刻・特徴・対応情報」。接続は **A04 → P01,A06,A09,A15**。純単眼のFrameを、一枚の画像に由来する観測と、その処理途中の情報を束ねる入れ物として読む。

## 画像から得た観測を同じ番号で結ぶ

特徴抽出は、画像の中から照合に使える位置と、その周辺の見え方を表す記述子を作る。追跡では、その特徴が既存のどの三次元地図点に対応するかを調べる。このためFrameには、二次元の特徴と三次元点への対応を別々に持ち、共通の特徴番号で結ぶ構造が必要になる。

入力はD05の画像・時刻の組と、校正情報・特徴抽出器である。単眼コンストラクタが特徴抽出と特徴座標の歪み補正を行い、後続のTrackingが対応点や姿勢を更新する。Frameを作っただけで姿勢推定や地図点との照合が完了するわけではない。

ORB（Oriented FAST and Rotated BRIEF、向きに対応する特徴点と二進記述子）の抽出理論はA04、歪み補正はD03を参照する。ここでは、それらの結果がどこへ入り、同じ特徴としてどう結び付くかを扱う。

## 特徴番号jを共有する配列

特徴があり、単眼コンストラクタの対応配列の初期化まで終えたFrameを対象に、特徴ごとの情報を次の組で整理する。これは説明用の記法であり、この名前の構造体が実装にあるわけではない。

\[
E_j=(u_j,\bar u_j,d_j,P_j,o_j),\qquad j=0,\ldots,N-1,\quad N>0.
\]

| 記号 | 型・次元・単位・コード上の意味 |
| --- | --- |
| \(N\) | 検出された特徴数を表す整数、コードは`int N`。地図点数や指定した抽出目標数ではない |
| \(j\) | 画像内の0始まりの特徴番号。FrameやMapPointの識別番号とは別 |
| \(E_j\) | 異なる型の五要素を束ねた組。三次元座標ベクトルではない |
| \(u_j\) | `mvKeys[j].pt`。元画像上の二成分の画素座標、単位pixel |
| \(\bar u_j\) | `mvKeysUn[j].pt`。歪み補正後の二成分の画素座標、単位pixel。上の横棒は補正済みという目印 |
| \(d_j\) | `mDescriptors.row(j)`。32個の符号なし8bit値からなる行、32 byte＝256 bitの二進記述子 |
| \(P_j\) | `mvpMapPoints[j]`。`MapPoint*`型の参照先、または`null`。三次元座標値そのものではない |
| \(o_j\) | `mvbOutlier[j]`。対応の外れ値分類を保持するbool値、単位なし |

両画素座標は画像右向きを横軸、下向きを縦軸とする。補正後も画素座標であり、正規化した視線とは異なる。KeyPointには位置以外に角度や尺度段などもあるが、式では位置だけを取り出した。記述子の各bitは局所的な明暗比較を表し、座標や距離の単位を持たない。

実際の記述子行列は、特徴がある通常の経路で**N行×32列の`CV_8U`**となる。行jと特徴jを取り違えると、ある位置の見え方を別の位置のものとして照合してしまう。Nは抽出結果なので、設定した目標個数が必ず得られるとは限らない。

## 未対応と外れ値を区別する

初期化時の対応点は全て`null`、外れ値フラグは全て`false`である。従って、`false`だけを見ても「良い三次元対応が得られた」とは判断できない。まず対応先があるか、その後どの検査を通ったかを分けて読む。

次はN＝3の仮定例であり、実動画の測定値ではない。追跡途中のある時点を切り取っている。

| j | 元画素 → 補正後画素（pixel） | 記述子 | 対応先 | 外れ値フラグ | 読めること |
| --- | --- | --- | --- | --- | --- |
| 0 | (100,200) → (103,201) | 行0、32 byte | 点Aへの参照 | false | 対応候補があり、現在フラグは立っていない |
| 1 | (640,360) → (640,360) | 行1、32 byte | null | false | 二次元特徴はあるが三次元点への対応はない |
| 2 | (1100,500) → (1096,499) | 行2、32 byte | 点Bへの参照 | true | 現在の対応が外れ値に分類された時点 |

`TrackReferenceKeyFrame`には、照合結果を対応配列に入れ、姿勢を最適化し、外れ値の対応先を`null`へ戻す経路がある。その際フラグも`false`へ戻すため、後で`null,false`を見ても「一度も外れ値にならなかった」とは言えない。この表の情報だけでFrame全体の追跡成功を結論することもできない。

純単眼の`mvuRight`と`mvDepth`は、それぞれN要素の`-1`で準備される。右画像の対応座標や直接の深度測定が入っていないことを示す番兵値であり、負の奥行きを実測したという意味ではない。地図点への対応があればその点の位置を別途参照できるが、二次元特徴自体が三次元点になるわけではない。

N＝0の場合は、抽出直後にコンストラクタから早期returnする。時刻保存やID採番は既に行われる一方、上記の対応配列代入や特徴の歪み補正、探索grid構築には進まない。「全Frameで全フィールドの初期化が同じ順で完了する」と一般化しない。

## Frame全体に付く状態と探索用情報

| 保持情報 | 役割と読み方 |
| --- | --- |
| `mTimeStamp`、`mnId` | doubleの画像時刻（秒）と、符号なし整数のFrame ID（Identifier、識別番号）。D05のとおり別管理 |
| `mTcw`、`mbHasPose` | 世界座標からカメラ座標への姿勢値と、その値が設定されたかを示すフラグ |
| `mpReferenceKF` | 参照KeyFrame（キーフレーム、地図の代表となる観測）へのポインタ。構築時はnullで、追跡側が設定する |
| `mBowVec`、`mFeatVec` | BoW（Bag of Words、特徴を語の出現としてまとめる表現）と、語彙木のノード別の特徴番号索引。D04の画像検索・照合用 |
| `mGrid` | 画像を格子セルに分け、近傍探索を速めるための特徴番号のリスト |

姿勢値の型は`Sophus::SE3<float>`で、回転と並進を持つ剛体変換である。回転成分は無次元、並進は単眼地図の任意尺度の長さであり、メートルが保証されるわけではない。世界→カメラの向きとカメラ中心の違いはA06/A09を参照する。

`SetPose`は値と派生行列を更新し、`mbHasPose`をtrueにする。最適化前の姿勢初期値にも呼ばれるため、`HasPose()==true`はTrackingの`OK`状態と同義ではない。姿勢値があることと、その画像の追跡が受理されたことを分ける。

単眼のgridは補正後の特徴座標からセルを求め、`PosInGrid`が成功した特徴番号だけを格納する。全特徴が必ず格子に入る保証や、地図点の三次元配置を保存する構造としては扱わない。BoW関連の計算は`ComputeBoW`が必要時に行い、Frame生成だけで全ての検索表現が完成したとも限らない。

コピーコンストラクタは、記述子を`clone`して画素記述のデータを複製する一方、地図点についてはポインタ列をコピーする。三次元点の実体を新たに複製する操作ではない。Frame IDも引き継ぐので、このコピーを新画像の採番と混同しない。これは確認したコピーコンストラクタの説明であり、全ての代入操作に同じ複製規則を断定するものではない。

## 理解確認

1. 特徴番号jは、記述子行・対応点・外れ値フラグのどこを結び付けるか。
2. `null,false`や`HasPose()==true`だけで、追跡成功を判断できるか。
3. Frameのコピーは、対応する三次元地図点の実体も複製するか。

答えの要点：同じ画像内の特徴jに属する欄／それだけでは判断できない／確認したコピーコンストラクタでは点へのポインタ列をコピーする。
