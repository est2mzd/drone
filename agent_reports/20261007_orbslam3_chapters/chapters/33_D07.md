# D07 キーフレーム検索用データベース

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「キーフレーム検索用DB」と、「辞書・検索用DB」のDB部分。接続は **KeyFrame登録 → A15,P03**。DBはDatabase（データベース）の略で、ここでは過去の代表画像を探すための索引を扱う。

## 語彙が決めた語から過去の画像を探す

再局在化や場所認識では、現在の画像と似た過去の観測を探したい。全ての過去画像の全特徴を初めから照合する代わりに、画像に含まれる「視覚的な語」を手掛かりとして候補を絞る。そのために、語から、その語を持つキーフレームへの逆向きの索引を用意する。

KeyFrame（キーフレーム）は地図の代表となる画像観測で、以下ではKFと略す。D04の事前語彙は、特徴記述子をどの語へ割り当てるかを定める。検索DBは、実行中に登録されたKFがどの語を持つかを保持する。この二つは役割も更新対象も異なる。

入力は登録・削除するKFとそのBoW（Bag of Words、画像を語の出現としてまとめる表現）、検索時には問い合わせ画像のBoWである。出力は再局在化やループ補正・地図統合に渡す**候補KFの参照**であり、確定した姿勢や地図の統合結果ではない。

## 転置索引を集合として読む

現行の`mvInvertedFile`は`vector<list<KeyFrame*>>`である。語番号でリストを選び、その語に登録されたKFポインタを取り出す。コンストラクタは事前語彙の語数に合わせて索引を用意する。地図点の座標を保存する容器でも、語彙木そのものでもない。

関係を理解するため、実リストから重複を除いた集合で次のように表す。

\[
I(w)=\{K\mid K\text{の参照が語}w\text{の索引に登録されている}\},
\qquad W_Q=\operatorname{supp}(v_Q),
\qquad C_0(Q)=\bigcup_{w\in W_Q}I(w).
\]

| 記号 | 型・意味・前提 |
| --- | --- |
| \(w\) | WordId、すなわち語の整数識別子。画像の特徴番号とは別 |
| \(K\) | 登録KFへの参照を表す記号。姿勢行列やカメラ内部行列ではない |
| \(I(w)\) | 語wの実リストから重複を除いて表したKF参照の有限集合 |
| \(Q\) | 問い合わせとなるFrameまたはKeyFrame。検索用途によって型が異なる |
| \(v_Q\) | Qの疎なBoWベクトル。語ごとに無次元の重みを持つ。計算方法はD04 |
| \(\operatorname{supp}(v_Q),W_Q\) | ベクトルの非零成分に対応する語番号の集合。suppはその集合を取り出す演算 |
| \(\bigcup,C_0(Q)\) | 集合和と、その結果。問い合わせのいずれかの語を共有する入口候補の概念集合 |

これらは識別子・参照・集合の関係で、画素座標や三次元距離の式ではない。問い合わせ語が空なら集合和も空になる。実装は共有語数の計数や問い合わせIDによる重複抑制も行うため、この式だけで候補順位や最終返却集合を再現することはできない。

集合式は登録の一意性を保証するものでもない。実際の`add`には重複登録の検査がなく、リストへ`push_back`する。正常な使用を説明する概念集合と、同じポインタが重複し得る実装上の容器を区別する。

## 登録・削除によって索引を更新する

| 操作 | 現行の処理 | 限定 |
| --- | --- | --- |
| `add(pKF)` | KFのBoWにある各語のリストへポインタを追加 | 特徴一つにつき一回ではなく、BoWの語エントリを走査する |
| `erase(pKF)` | KFのBoWにある各語をたどり、そのリストの最初の一致を削除 | 同じ語に重複登録があれば全件削除とは限らない |
| `clearMap(pMap)` | 全語のリストを走査し、所属Mapが指定Mapと一致する項目を削除 | KF実体をこの関数でdeleteする処理ではない |
| `clear()` | 索引全体を空にし、語彙サイズの空リスト群へ戻す | 事前語彙を学習し直す操作ではない |

`add`、`erase`、`clearMap`はmutexを取得して索引を変更する。`clear`の関数内には同じlockがないので、全操作が同じ方法で保護されるとは一般化しない。これは読んだ関数の範囲の説明で、全並行動作を検証したものではない。

登録は明示的な呼出しで行う。例えばLoopClosingは小地図の早期終了経路や、候補検証を終えた経路で現在KFを追加する。普通の全Frameが自動登録されるわけではなく、全生成KFの登録もこの容器が保証するものではない。LoopClosingのキュー挿入にはID＝0を除外する条件もある。

KFの無効化処理には、Map側からの除去とは別にDBの`erase`を呼ぶ箇所がある。現在Mapのリセットでは`clearMap`が呼ばれる（A21）。本章が扱う検索本体はメモリ上の索引であり、保存用の別フィールドや永続化処理の詳細には立ち入らない。

## 共有語から幾何検証へ進む

入口では共有語を持つ候補を集め、その語数を使って評価対象を絞り、語彙の`score`でBoWの類似度を計算する。さらに共視近傍、すなわち同じ地図点を観測する近隣KFの関連スコアを集約し、候補を選ぶ。一枚だけの外観類似を、関連する観測群と合わせて扱うためである。

この共視は三次元の距離半径で決める近さではない。BoW類似度の定義はD04、共有観測による関係はA10を参照する。集約スコアを、その場所である確率や幾何誤差の保証として解釈しない。

| 呼出し先 | 問い合わせと候補の扱い | 次に行うこと |
| --- | --- | --- |
| `DetectRelocalizationCandidates` | 現在Frameで検索し、返却候補へ入れる直前に指定Mapとの一致を検査 | A15で特徴と既存点を対応させ、姿勢仮説を幾何検証 |
| `DetectNBestCandidates` | 現在KFと接続しているKFを入口で除き、評価・共視集約後、同Mapをloop、別の非bad Mapをmerge候補へ分ける | P03で各候補群を別々の幾何検証へ渡す |

再局在化の呼出し元は現在Mapを引数に渡す。ただし、そのMapによる制限は**返却前のフィルタ**である。共有語の収集、語数による選別、スコア・共視集約の最初から他Mapを除外しているとは説明しない。Atlasが複数Mapを持つことと、A15の返却候補が現在Mapに限られることは両立する。

LoopClosingは`DetectNBestCandidates(...,3)`を呼び、現行関数はloopとmergeの出力をそれぞれの個数条件で扱う。「両方合わせて必ず3件」「同一地図だけを検索する」という説明にはならない。旧論文の候補規則を全て現行へ転記せず、検証と補正・統合の詳細はP03へ渡す。

## 三つのKFで索引を読む例

仮に`I(w1)={K1,K2}`、`I(w2)={K2,K3}`で、問い合わせ語が`{w1,w2}`なら、入口の集合は`C0={K1,K2,K3}`となる。K2は二つの語に現れるが、集合では一つとして表す。これは実動画から測定した索引ではない。

K1/K2がMap A、K3がMap Bに属していても、上の集合和自体はK3を除かない。その後のスコア・共視・出力条件で候補は変わる。A15で指定MapがAなら、最終返却候補にK3は入らない。P03では、現在KFがAに属するとき、残った同Map候補と別Map候補を用途別に分ける。共有語があることだけでは、K1/K2/K3のいずれとの幾何一致も確定していない。

## 理解確認

1. 事前語彙と検索DBは、それぞれ何を保持するか。
2. 集合I(w)で重複を除く説明は、addの重複登録禁止を意味するか。
3. 現在Mapへの再局在化では、どの段階でMap条件が適用され、返却後に何が残るか。

答えの要点：語の割当規則と登録KFへの索引／意味しない／返却直前に絞り、特徴対応・姿勢の幾何検証が残る。
