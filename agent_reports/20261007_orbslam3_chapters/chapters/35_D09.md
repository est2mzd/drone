# D09 KeyFrameと受け渡し

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「選ばれたKeyFrame」と「処理したKeyFrame」。接続は **A06/A13 → P02 → P03**。純単眼の処理で、代表観測を地図更新・場所認識へ渡すデータとキューを扱う。

## 一枚の観測を地図の代表として残す

Frameは入力画像ごとの特徴や追跡途中の情報を持つ。全画像を同じ重さで地図処理へ送ると計算量が増えるため、通常追跡では条件を満たした観測からKeyFrame（キーフレーム、以下KF）を作る。どの画像を選ぶかはA13、最初の二つを作る特別な経路はA06を参照する。

入力は選ばれたFrameと、所属Map・検索DB（Database、データベース）への参照である。コンストラクタは特徴や時刻などを引き継いだKFを作る。そのKFへのポインタがLocalMappingの入力となり、処理経路からLoopClosing側へも渡される。

KFは画像ファイルを一枚保存したもの、という理解では足りない。画像内の特徴、地図点への関連、姿勢、他のKFとの接続を持ち、地図の修正に合わせて変わる情報もある。

## 元Frameから何を引き継ぐか

| 情報 | 現行コンストラクタの扱い |
| --- | --- |
| 元Frameの識別番号と時刻 | `mnFrameId=F.mnId`、`mTimeStamp=F.mTimeStamp`。どの入力観測に由来するかを残す |
| KF自身の識別番号 | KeyFrame側の`nNextId++`で`mnId`を採番。元Frame番号の転記ではない |
| 特徴と記述子 | 特徴配列をコピーし、`mDescriptors`は`clone`してデータを複製する |
| 地図点への対応 | `mvpMapPoints`のポインタ列をコピー。同じMapPoint実体を参照する |
| 検索用情報 | BoW（Bag of Words、画像を語の出現で表す情報）・特徴索引と、探索gridを引き継ぐ |
| 校正・姿勢・所属 | 校正値やカメラ・語彙への参照、所属Map等を持ち、`SetPose(F.GetPose())`で姿勢を設定する |

IDはIdentifier（識別番号）の略で、KFの`mnId`は`long unsigned int`、`mnFrameId`は`const long unsigned int`である。時刻は`const double`の秒値で、姿勢の最適化を行った処理時刻ではない。元Frame番号と時刻の生成はD05を参照する。

記述子をcloneしていることから、全ての保持情報を実体ごと複製しているとは言えない。特に地図点やカメラ・語彙は参照であり、KFを増やすたびに既存の三次元地図点を丸ごと作り直す処理ではない。

## 特徴と地図点を結ぶ最小の関係

単眼KFの対応欄を、次のような関係として読む。

\[
\mathcal O_K(j)=K.\mathrm{mvpMapPoints}[j],\qquad 0\le j<N_K.
\]

| 記号 | 型・意味・単位 |
| --- | --- |
| \(K\) | 一つのKeyFrameオブジェクト。カメラ内部行列を表す記号ではない |
| \(N_K\) | Kが持つ特徴数、整数。対応済み地図点数とは限らない |
| \(j\) | 0始まりの画像内特徴番号、整数。KFのIDやMapPointのIDとは別 |
| \(\mathcal O_K\) | 特徴番号から、その時点の対応欄へ引く関係を表す説明用記法 |
| \(\mathcal O_K(j)\) | MapPointへの参照、またはnull。三次元座標値そのものではなく、長さの単位を持たない |

特徴座標の単位はpixel、記述子行との共通添字はD06のとおりである。この式は幾何変換ではない。KF側に点への参照をコピーしたことと、MapPoint側の「どのKFに観測されたか」を登録したことも別の操作であり、LocalMappingなどが必要な観測関係を整える。

例えば元FrameのIDが120、時刻が4.0秒、KeyFrame側の次の番号が7だと仮定する。このFrameから作ったKFは`mnId=7`、`mnFrameId=120`、`mTimeStamp=4.0`となる。番号120から時刻を算出したという意味ではなく、既にある三つの値の役割を示した例である。

元Frameの特徴j＝2が点Pを参照し、特徴数が3以上なら、構築直後の`O_K(2)`も同じPを指す。記述子は別データへ複製されても、点Pの実体は増えない。その後KFの姿勢や点との対応を修正しても、元Frame番号と入力時刻の役割は変わらない。この例は実動画の計測結果ではない。

## 変わる情報と残す情報

KeyFrameには、姿勢を更新する`SetPose`、対応先を追加・解除・交換する操作、共視接続を更新する操作がある。記述子などの保持欄にconstがあることを、KF全体が不変であるという意味に広げてはならない。

姿勢はD08の世界→カメラ変換で、局所最適化やループ補正等によって修正され得る。観測先や接続も更新されるため、キューへ入れた時点のKFを、地図の最終結果が固定されたスナップショットと見なさない。具体的な最適化・融合の処理はP02/P03を参照する。

## Trackingから二つのキューへ

```text
A06 初期化: 初期Frame/現在Frame → 初期2KF → Map登録 ┐
                                                      ├→ LocalMappingキュー
A13 通常追加: 現在Frame → 新KF ────────────────────────┘
    ↓ LocalMappingが取り出す
必要なBoW・観測・共視接続・Map登録を処理 → 条件に応じた地図処理
    ↓ 同じKFへのポインタを渡す
LoopClosingキュー（ID≠0を受け付ける） → P03の処理
```

初期化では二つのKFを構築し、先にAtlas経由でMapへ登録してからLocalMappingへ投入する。通常の追加では、作成抑止条件を通過してKFを構築し、キューへ投入する。通常側のMap登録はLocalMappingの`ProcessNewKeyFrame`内で行う。この登録順を一律に説明しない。

`LocalMapping::InsertKeyFrame`は、mutex下でKFポインタをキュー末尾へ追加し、局所バンドル調整（Bundle Adjustment、姿勢と点を調整する最適化）への中断要求フラグを立てる。関数が戻ったことは、観測更新や最適化が完了した証明ではない。

LocalMappingがキュー先頭から取り出すと、必要なBoW計算、地図点側の観測登録、共視接続の更新、Map登録へ進む。その後の地図処理には条件分岐や中断がある。RunからLoopClosingへ渡されたことも、毎回局所最適化が実行され収束したという保証にはならない。

`LoopClosing::InsertKeyFrame`もキューへポインタを積む操作であり、現行はID＝0を除外する。全KFがそのまま場所認識へ受理されるわけではなく、キュー投入とP03の幾何検証・補正・統合の完了を分けて読む。検索DBへの登録も別の明示的処理である（D07）。

## 理解確認

1. KF自身のID、元FrameのID、入力時刻はどのように保存されるか。
2. 記述子のcloneとMapPointポインタ列のコピーは、何が異なるか。
3. LocalMappingやLoopClosingのキューに入ったことは、何の完了を保証しないか。

答えの要点：KF IDは別採番、元ID・時刻は継承／前者はデータ複製、後者は同じ点への参照／観測更新・最適化・幾何検証や補正の完了を保証しない。
