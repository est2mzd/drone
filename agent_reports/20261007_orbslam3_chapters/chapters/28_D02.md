# D02 FPSと時間基準

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「動画のFPS」。接続は **動画情報 → A03,D05**。FPS（Frames Per Second）は毎秒の画像数を表し、現行wrapperでは画像番号から時刻を作るための入力となる。

本章は画像読込の活動を繰り返す章ではなく、その計算に使うレートと時間基準を整理する。画像の内容はD01、画像と時刻を本体へ渡す処理はA03、組としてのデータはD05を参照する。

## FPSから何を作るのか

画像の順番だけでは、二枚の間が何秒だったかは分からない。現行wrapperは起動時に一度`CAP_PROP_FPS`を取得し、画像が一定間隔で並ぶとみなして、先頭を0秒とする時間ラベルを作る。

入力はOpenCV（Open Source Computer Vision Library、画像・動画処理ライブラリ）が返すレート情報。出力はwrapperが採用する`double fps`で、A03が各画像の`timestamp`を計算するときに使う。`get`した値は撮像間隔を実測した結果とは限らず、実際の挙動は動画読込のバックエンドなどに依存する。

## 採用値の決め方と、等間隔の時刻式

取得値を\(f_{\mathrm{raw}}\)、採用値を\(f\)とすると、現行の分岐は次のとおりである。定数1と30も、ここでは画像数/秒を表す。

\[
f=\begin{cases}
30 & f_{\mathrm{raw}}<1\text{ の比較が真のとき},\\
f_{\mathrm{raw}} & \text{それ以外}.
\end{cases}
\]

例えば取得値が0や0.5なら30へ置き換わり、1なら1、29.97なら29.97を使う。この置換は処理上の規則であり、元の映像が30FPSで撮影されたと認定する処理ではない。

公式文書は、未対応プロパティに対して`get`が0を返す場合を説明している。一方、コードは`fps<1.0`だけを検査し、有限性を確かめる処理はない。非有限値を含む全ての不適切な値が30へ直るとは保証できず、それらの値が今回の動画で発生するかも未検査である。

以下の時刻式は、採用値\(f\)が**有限かつ正**で、一定レートの画像列とみなす場合の数学的な整理である。

\[
t_k=\frac{k}{f},\qquad
\Delta t=t_{k+1}-t_k=\frac{1}{f},\qquad
t_{N-1}=\frac{N-1}{f}\quad(N\ge1).
\]

| 記号 | 型・単位・意味 |
| --- | --- |
| \(f_{\mathrm{raw}}\) | `CAP_PROP_FPS`から得てdoubleへ格納する数値。想定単位は画像数/秒。非有限値を網羅的に排除する検査はない |
| \(f\) | 分岐後に採用するレート。時刻式では有限な正の実数、単位は画像数/秒 |
| \(N\) | 入力した画像の枚数を表す非負整数。単位は枚数で、最終時刻の式は1枚以上の場合だけ |
| \(k\) | 0始まりの画像番号。整数で\(0\le k<N\)。`frame_index`に対応する順番で、日時ではない |
| \(t_k\) | 画像kへ付ける実数の相対時刻。単位は秒、先頭の画像は0秒 |
| \(\Delta t\) | 隣接する生成時刻の差。単位は秒。比較する二枚がある\(0\le k<N-1\)で定義する |

これは時間軸の式であり、世界・カメラ・機体の空間座標を扱わない。コードは画像番号をdoubleへ変換して割るため整数除算ではないが、浮動小数点演算の丸めはある。式そのものが個々の露光時刻を復元するわけではない。

## 30FPSでの小さな例

採用値が30の場合、モデル上の間隔は1/30秒、約0.0333秒になる。次の値は計算例であり、実動画の計測値ではない。

| 0始まりの画像番号k | 付ける時刻 |
| --- | --- |
| 0 | 0秒 |
| 1 | 1/30秒、約0.0333秒 |
| 29 | 29/30秒、約0.9667秒 |
| 30 | 1秒 |

30枚だけなら番号は0〜29なので、最後の画像時刻は29/30秒である。31枚目が存在して初めて番号30の画像へ1秒を付ける。`N/f`を最後の画像のtimestampとして扱わない。また、最後の画像時刻だけからファイル全体の再生時間を確定するものでもない。

## 似て見える時間を分ける

| 時間・情報 | 意味と現行での扱い |
| --- | --- |
| 生成した画像時刻 | 上の番号/FPS式による相対秒。`TrackMonocular`へ渡す値 |
| 実際の撮像時刻 | カメラが露光した時点。wrapperは画像ごとの撮像時計を取得しない |
| PTS（Presentation Time Stamp、提示時刻） | 映像をいつ提示するかを表す時刻情報。現行wrapperは各画像のPTSを取得して使わない |
| `CAP_PROP_POS_MSEC` | OpenCVが定義する動画内の現在位置、単位はミリ秒。現行wrapperは取得しない。これだけでカメラの撮像時計と同一とは言えない |
| `steady_clock`の差 | 画像ループ開始直前から終了・保存後までの経過時間。本体構築は含まず、待ちや入出力は含む。画像のtimestampには使わない |

画像の間隔が不均一だったり記録に欠落があったりすると、一つのFPSから作る等間隔時刻ではその時間構造を表せない場合がある。提示時刻や動画内の現在位置も、露光した絶対日時と無条件に同じ情報ではない。

さらに、1/30秒刻みのtimestampを付けることは、実時間で毎秒30枚を処理する制御ではない。wrapperのループにFPSへ合わせる待機処理はない。本体内部の待機の有無や処理速度を、この式から判断することもできない。A17の復帰時間判定が参照する画像時刻へのつながりは、同章を参照する。

## 設定ファイルのCamera.fpsは別の経路

| 値の経路 | 現行の用途 |
| --- | --- |
| 動画→`CAP_PROP_FPS`→wrapperの`fps` | 上記の規則で採用し、`frame_index/fps`から画像時刻を作る |
| 設定ファイル→`Camera.fps`→`mMaxFrames` | Tracking内の画像番号に基づく判定へ使う。A11/A13などの条件に関係する |

現行`mini3_calib/out/mini3.yaml`は`File.version: "1.0"`、`Camera.fps: 30`である。この経路は`Settings`が整数として読み、floatの保持値・アクセサを経て、Trackingの整数`mMaxFrames`へ代入する。動画から得たdoubleのFPSを設定値へ上書きする経路ではない。

例えば動画側の採用値が60でも、設定が30なら`mMaxFrames`は30のままである。画像番号30への生成時刻は0.5秒となるが、設定の数値が自動で60へ変わるわけではない。個々の判定はほかの条件も含むため、「必ず30枚ごとに処理する」といった周期の保証へは読み替えない。

## 現行コード・実読資料・限界

確認日2026-10-07。主HEAD `d1265bc35439dd6ca57687ac93c8b3a7310fc681`、ORB_SLAM3 HEAD `4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4`。wrapperは`slam/src/offline_mono.cpp:33-36,42-54`がFPS/時刻、同`:44,65-66`が処理経過時間。本体は`third_party/ORB_SLAM3/`以下の`src/System.cc:82-84`、`src/Settings.cc:410`、`include/Settings.h:82,170`、`src/Tracking.cc:584-586`、`include/Tracking.h:302`が現行設定経路である。

[OpenCV 4.6 VideoCapture::get](https://docs.opencv.org/4.6.0/d8/dfe/classcv_1_1VideoCapture.html)と[プロパティ定義](https://docs.opencv.org/4.6.0/d4/d15/group__videoio__flags__base.html)のFPS・POS_MSEC・バックエンドの注記を実読した。[ORB-SLAM3論文](https://arxiv.org/pdf/2007.11898v2)のPDF5頁図1・§IIIも本文と画像で再読したが、これは画像入力と追跡の位置付けの根拠であり、自前wrapperの`k/f`や30への置換を規定する資料ではない。

根拠は[D02調査メモ](../research/D02_evidence.md)。実動画のFPS・個別時刻・可変レート・欠損・設定との一致、実リンク版とバックエンドは未検査。動画実行や設定変更は行っていない。

## 理解確認

1. 動画から0FPSが返り30へ置き換わったら、撮像レートが30だと確認できたか。
2. 30FPSの30枚目の画像（番号29）には何秒を付けるか。
3. 動画の採用FPSが60なら、設定由来の`mMaxFrames=30`も自動で60へ変わるか。

答えの要点：代替規則であり実測ではない／29/30秒／独立した入力経路なので自動では変わらない。
