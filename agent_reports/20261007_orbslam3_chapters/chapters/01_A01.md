# A01 入力一式の準備

## 図の位置と、この章で扱うこと

元の図Aの **[動画・校正・特徴の辞書を用意する]** に対応する。接続は **開始 → A01 → A02「次の画像がある?」**。データフロー図では別々に描かれた「保存動画」「校正」「特徴の辞書」を、処理開始前にそろえる活動である。

本章は三入力の役割と整合条件を扱う。校正の幾何はD03、辞書の検索理論はD04、画像の読み出しと時刻はA03で詳しく学ぶ。

## 背景：画像だけでは、写り方と検索の準備が足りない

保存動画には、カメラが見た画像が時間順に入っている。しかし画像中の点を3次元の位置関係へ結び付けるには、そのカメラがどのように景色を画像へ写すかも必要になる。その情報がカメラモデルと校正値である。

さらに、以前の画像と似た場所を探すために、ORB（Oriented FAST and Rotated BRIEF：画像の目印を検出し、その見た目を記述子という数値で表す方式）の特徴を整理する「視覚語彙」を使う。語彙はその見た目を分類するための事前資料で、観測画像や撮影場所の3次元地図とは役割が違う。

論文の図1では、入力FrameからのORB抽出と、DBoW2（Dynamic Bag of Words 2：画像の特徴を視覚単語の集まりとして表し、検索するライブラリ）のVisual Vocabulary（視覚語彙）が別の場所に描かれている。カメラモデルはIV節で独立した機能として説明される。これが三入力を分けて考える背景である。[論文PDF、5頁・図1、6頁・IV節](https://arxiv.org/pdf/2007.11898v2)

## 目的と入出力

目的は、**同じ撮影条件を指す動画とカメラ設定、およびORB記述子用の語彙をそろえ、画像処理を始められる状態にすること**。語彙をこの動画の撮影場所で学習し直すことが起動の条件ではない。ここを終えても、撮影場所の初期3次元地図はまだ成立していない。

| 入力 | 担当する役割 | 現行プロジェクトでの指定 |
| --- | --- | --- |
| 保存動画 | 観測する画像列を供給する | 利用者が動画パスを指定する |
| カメラ設定YAML | 画像の写り方と処理設定を供給する | `mini3_calib/out/mini3.yaml` |
| ORB語彙 | ORB記述子を使う画像検索の準備をする | `third_party/ORB_SLAM3/Vocabulary/ORBvoc.txt` |

YAMLは名前付きの設定値を書くファイル形式である。今回のファイルは校正値のほか、画像サイズ・色順・FPS（Frames Per Second：1秒当たりの画像数）・ORB抽出器・表示の設定も含む。「校正ファイル」と呼んでも、内容全部が校正値というわけではない。

出力は、開いた動画入力と、設定・語彙・検索用データベース・Atlasの器を用意した単眼SLAM（Simultaneous Localization and Mapping：自己位置推定と地図作成を同時に行うこと）の処理系である。Atlasは地図群を保持する入れ物。初期地図を作れるかは、その後の画像の対応を使うA06/A07で判定する。保存先ファイルのパスも必要だが、それは観測や校正を与える三入力には数えない。

## 理論：読めることと、組合せが正しいことを分ける

準備には二つの段階がある。まずファイルを開けて、必要な形式と項目で読めること。次に、動画と設定が同じ観測条件を表し、語彙が処理する特徴の種類に対応していることである。

たとえば、別のカメラの校正でも、YAMLとしては正しく読める。正しい型の数値が並んでいるだけでは、今回の動画の写り方に合っているとは証明できない。公式READMEも、自分のカメラを校正して設定YAMLを作る手順を示している。[公式README「Running ORB-SLAM3 with your camera」](https://github.com/UZ-SLAMLab/ORB_SLAM3#4-running-orb-slam3-with-your-camera)

現行設定はピンホール系モデル `PinHole`、元画像1280×720、色順設定 `Camera.RGB: 0` を指定する。0は3チャネル画像をBGR、すなわち青・緑・赤の順として扱う指定である。実動画の色順を自動判定した結果ではない。

この設定を使うなら、動画が同じカメラ・解像度・撮影と画像処理の条件に対応するかを確認する。クロップ、デジタルズーム、外部での歪み補正などで写り方が変われば、同じ解像度でも校正との対応を再確認する必要がある。語彙ファイルの変更では、この不一致を直せない。

## 必要な式：入力の組と、寸法の整合条件

次の式は本章の整理用であり、論文から借りた推定式ではない。

\[
\mathcal{X}=(V,C,L),\qquad
\operatorname{size}(I_k)=(H_C,W_C)=(720,1280).
\]

| 記号 | 型・次元・単位・意味 |
| --- | --- |
| \(\mathcal{X}\) | 異なる型の三要素をまとめた組。数値ベクトルではなく、単位なし |
| \(V\) | 保存動画データ。コードではそのファイルパスを文字列で渡す |
| \(C\) | 読み込んだ設定項目の集合。項目ごとに型・単位を持つ |
| \(L\) | ORB視覚語彙というデータ構造。長さや地図の座標ではない |
| \(k\)、\(I_k\) | \(k\)は0以上の整数の画像番号、単位なし。\(I_k\)は本体へ渡す第\(k\)画像の画素配列。カラーでは各画素に複数チャネルを持つ |
| \(\operatorname{size}\) | 画素配列のチャネル数を除き、**高さ、幅**の順で返す操作 |
| \(H_C,W_C\) | \(C\)に指定した元画像の高さ・幅。正整数で、単位は画素 |

前提は、現行YAMLにリサイズ指定がなく、校正と同じ撮影・画像処理条件の画像を渡すことである。画像座標は左上原点、横は右向き、縦は下向き、単位は画素とする。本章の式に世界座標や機体座標は登場しない。

この等式は満たすべき整合条件の一つであり、コード中の自動検査式ではない。**寸法が一致しても、校正の正確性や追跡成功までは保証しない。**

呼出しの対応は次のとおり。これは引数の説明であり、今回実行した記録ではない。

```text
利用者 → run.sh VIDEO [POINTS_TXT]
スクリプト → offline_mono VOCABULARY SETTINGS VIDEO POINTS_TXT
```

語彙はORB用の**テキスト形式**を読む。現行YAMLは`File.version: "1.0"`なので、旧経路の`Camera.fx`ではなく`Camera1.fx`等が使われる。また、古いローカルREADMEには別の設定パスが残るため、本章は実際の`run.sh:13`を基準にした。

読込失敗は動画なら`main:28-30`、設定なら`System.cc:75-79`、語彙ローダが失敗を返した場合なら`System.cc:123-128`で終了する。しかし確認した入力経路には、実画像の幅・高さをYAMLの宣言値と比較して拒否する処理はない。`Camera.fps`と動画から取得するFPSも別に読み込まれ、自動で同じ値にそろうわけではない。

## 具体例：同じ設定で縮小動画を渡すとどうなるか

説明用に、校正と同じ撮影条件の1280×720動画を指定したとする。動画は`VideoCapture`へ、YAMLと語彙は`System`へ渡る。画像サイズは上の整合条件を満たすが、それだけで校正品質や初期化の成功が決まるわけではない。

その動画を外部で640×360へ縮小し、YAMLをそのまま使うと、画像の画素位置と校正値の対応が変わる。現行経路は寸法の違いだけを理由には拒否しないため、起動できたことを正しさの証拠にできない。必要なのは、実際の画像変換と校正値の対応をそろえることである。その具体的な計算はD03で扱う。

## 成立条件と限界

- 動画のデコード、対応する設定の解釈、ORB語彙の読込が必要。形式の読込と、内容の適合は別に確かめる。
- 本章は静的なコード・資料調査である。特定動画の実寸・色順・撮影条件・実行結果や、校正値の品質は実測していない。
- YAMLコメントには校正結果が記されているが、今回その校正を再検証したわけではない。
- 入力準備だけでは、地図の成立、メートル単位の尺度、カメラと機体の位置関係は得られない。

4. A01の出口で初期地図は成立しているか。次に進む図のブロックは何か。

答えの要点：観測画像・写り方等の設定・検索用語彙／読込検査は撮影条件の一致を証明しない／画素位置と校正値の対応／まだ成立しておらず、A02で次の画像の有無を調べる。
