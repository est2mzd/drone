# A16 再局在化の成立判定

## 図の位置、背景と目的

図Bの **<復帰できた?>** に対応する。A15の再局在化から入り、**はい→A10の局所地図確認、いいえ→A17の試行継続判断**へ進む。対象は純単眼・通常SLAMである。SLAMはSimultaneous Localization and Mapping、自己位置推定と地図作成を同時に行う処理を指す。

姿勢仮説が得られても、観測に十分支えられているとは限らない。また、一つの候補が不成立でも別の候補を試せる場合がある。本章は、候補の評価と再局在化関数の受理、さらに呼出し側の最終追跡状態を分けて説明する。

入力はA15で得た候補姿勢、対応、最適化後の評価、候補の試行状況である。出力は`Relocalization`の真/偽と、受理した場合の画像番号の更新である。Frameは現在画像の特徴・姿勢等を持つ入れ物であり、関数の真だけで`Track`全体の最終状態まで確定しない。

## 数値と真偽値の役割

\(g\)を`nGood`、\(h\)を`nadditional`とする。どちらも0以上の整数で単位は対応の個数、空間座標や画素誤差ではない。\(g\)は各`PoseOptimization`の戻り値で、呼ぶたびに上書きされる。\(h\)はその投影探索で追加した対応数であり、まだ同じ最適化で検証した数とは限らない。

`PoseOptimization`の通常終了では、入力した対応数から最後に外れ値と分類した数を引いて返す。初期対応が少なすぎる場合には早期に0を返す経路もある。これを、登録観測数まで条件にして数え直すA11の`mnMatchesInliers`と同じ計数処理とは扱わない。

| 変数 | 何を示すか |
| --- | --- |
| `bNoMore` | その候補の今後の試行を終了する情報 |
| `bTcw` | 今回のソルバ呼出しが姿勢を返したか |
| `bMatch` | 関数内で受理できる候補が見つかったか |
| `bOK` | 呼出し側`Track`が各処理の結果を受け、後から更新する成否 |

これらは全て真/偽であり、物理単位を持たない。`bNoMore=true`なら候補に破棄印を付けて残数を減らすが、その直後に`continue`するわけではない。続けて`bTcw`を確認するため、**今後の試行終了と、今回返った姿勢の評価は両立する**。ソルバにも両方が真になる経路がある。

## 候補評価は順序を持つ

`bTcw=true`なら、まず姿勢とその整合対応を現在Frameへ設定し、`PoseOptimization`を実行する。以下はその最初の\(g\)を得た後の順序である。

| 評価段階 | 条件と動作 |
| --- | --- |
| 最初の関門 | \(g<10\)なら、その候補の今回の残りの評価を飛ばし次候補へ進む。この`continue`自体は候補破棄印を付けない |
| 広い範囲の追加探索 | 上の関門を通り\(g<50\)なら投影探索で\(h\)を得る。\(g+h\ge50\)の場合に再最適化し、\(g\)を更新する |
| さらに狭い探索 | **広い探索後の再最適化を行い**、更新後が\(30<g<50\)なら狭い探索を行う。その\(g+h\ge50\)なら再び最適化して\(g\)を更新する |
| この候補の受理 | 最後に得た\(g\ge50\)なら`bMatch=true`にして候補ループを抜ける |

追加探索の合計\(g+h\)は、再最適化へ進む条件である。追加しただけで受理するのではなく、最後の最適化戻り値で受理を決める。この候補の末尾における述語は次のように書ける。

\[
B(g)=(g\ge50).
\]

\(B\)は対応数から真/偽を返す受理述語、50は対応の個数である。前提はその候補の処理末尾まで到達し、必要な再最適化を経た\(g\)であること。途中の仮説対応数、追加前の値、別の候補の値へ無条件に適用する式ではない。

候補探索を終えたとき`bMatch=false`なら、関数は偽を返す。真なら`mnLastRelocFrameId=mCurrentFrame.mnId`を記録して真を返す。記録するのは整数のFrame識別番号であり、秒単位の時刻ではない。

姿勢はこの最終判定より先にFrameへ設定される。したがって、関数が偽を返したことを「Frameの姿勢が必ず未設定または空に戻った」と解釈しない。**姿勢仮説の格納と、その受理は別**である。

## 関数の真から最終追跡状態まで

呼出し側は`bOK=Relocalization()`とし、真なら同じ画像についてA10の`TrackLocalMap`を実行する。その戻り値で`bOK`を上書きし、最後の`bOK`が真の場合に`mState=OK`へ更新する。`OK`は追跡を受理した状態を表す。

このため、再局在化関数の真や最終再局在画像番号の更新だけでは、後の局所地図確認まで通過したとは言えない。関数が偽なら図のA17へ接続するが、試行を続ける時間条件は本章では扱わない。

## 境界の例、限界と出典

最初の\(g=9\)は次候補へ進み、\(g=10\)なら追加探索側へ進める。広い探索後の再最適化で\(g=30\)なら狭い探索条件を満たさず、31〜49なら満たす。いずれも、その数だけで候補を受理したことにはならない。

例えば40対応に10対応を追加すると、再最適化を行う条件を満たす。その結果が49なら**その時点では未受理だが、さらに狭い探索で改善し得る**。その候補で最後に得た最適化結果が49なら受理せず、50なら受理する。一候補の未受理だけで、他候補も含む関数全体の偽が確定するとは限らない。

これらは判定規則への入力を仮定した例であり、実動画の数値を測定したものではない。50対応に支えられた受理も、真の姿勢誤差が一定以下という証明や、次画像の追跡成功の保証ではない。

[固定コミットの公式Tracking.cc](https://raw.githubusercontent.com/UZ-SLAMLab/ORB_SLAM3/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc)を照合し、[ORB-SLAM原論文](https://arxiv.org/pdf/1502.00956v2)のPDF8頁＝誌面7頁・V.Cを本文と画像で再読した。論文の最適化・追加探索・十分な整合対応という説明と、現行の10/30/50および真偽値の制御順を区別する。詳細は [A16調査メモ](../research/A16_evidence.md)。

## 理解確認

1. `bNoMore=true`なら、今回の返却姿勢も必ず評価しないか。
2. 40対応に10対応を追加しただけで、候補を受理するか。
3. `Relocalization=true`なら、`Track`の最終状態も直ちに`OK`と確定するか。

答えの要点：`bTcw`が真なら評価する／再最適化後の数で判定する／さらに局所地図確認の結果を反映する。
