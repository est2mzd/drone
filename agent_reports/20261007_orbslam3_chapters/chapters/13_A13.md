# A13 姿勢を得てキーフレームを選ぶ

## 図の位置、背景と目的

図Aの **[姿勢を得る・必要ならキーフレームを選ぶ]** に対応する。A07/A11の成立側からつながり、姿勢はD08、選んだKeyFrameはD09を経てP02のLocalMappingへ渡る。画像処理は合流点Aから次画像へ続く。

KeyFrameは地図用に残す重要画像である。毎画像を残すと処理量が増える一方、古い視点だけを使い続けると、新しく見えた場所を地図へ取り込む機会が減る。そこで、追跡結果、参照画像との対応数の違い、画像間隔、地図更新側の受付状態を用いて追加を判断する。

対象は現行の**純単眼・通常SLAM、一カメラ設定**である。SLAMはSimultaneous Localization and Mapping、自己位置推定と地図作成を同時に行う処理を指す。初期地図がある状態での通常追加を中心にし、地図更新側の内部処理はP02へ残す。

## 入出力と初期化との境界

入力は現在Frameの姿勢・特徴・既存MapPointとの対応、追跡成否、参照KeyFrame、各Frame番号、LocalMappingの状態である。Frameは一画像の情報をまとめる入れ物、MapPointは3次元地図点、LocalMappingは地図更新を担当する処理である。

追跡が成立すると、現在Frameには世界座標から現在カメラ座標への姿勢`Tcw`が得られている。単眼の並進は任意の地図長さ単位であり、メートルとは限らない。姿勢の意味と計算は [A09](09_A09.md) を参照する。`NeedNewKeyFrame`が姿勢を新たに計算するわけではない。

追加が必要で生成側の条件も通れば、新KeyFrameを作り、LocalMappingの処理待ちの列（キュー）へ入れる。追加しなくても、その画像の追跡結果を得たこととは両立する。**追跡成功、追加必要、生成、地図処理完了は別の段階**である。

A07からの矢印は、A06で初期二枚のKeyFrameと地図・姿勢を得た結果の接続である。初期化成功と同じ`Track`呼出しが、通常追跡側の`else`へ入り直して`NeedNewKeyFrame`も実行するわけではない。初期二枚の作成はA06の別経路である。

## 通常追加の入口と早期抑止

`Track`は`bOK || mState==RECENTLY_LOST`の範囲で`NeedNewKeyFrame`を評価する。ただし純単眼で`CreateNewKeyFrame`を呼ぶ条件は、**必要判定が真、かつ`bOK`も真**である。`bOK`は現在処理の成否、`RECENTLY_LOST`は最近追跡を見失った状態を表す。

通常SLAMではまず、LocalMappingが停止中または停止要求中なら必要判定を偽にする。また、後述の番号を使って`i < r + M`かつ`K > M`なら偽にする。これは再局在化付近の追加を抑えるFrame番号と地図規模の条件であり、常に一定の秒数だけ禁止する処理ではない。

再局在化は既存地図上の現在位置を探し直す処理である。保存番号`r`の初期値は0なので、この番号条件を実際の再局在化成功後だけに限ると解釈しない。位置推定専用モードも追加を抑止するが、現行の通常SLAMではそのモードは無効である。

## 純単眼の候補条件

次の記号は現行コードを簡約して説明するためのもので、論文の原式ではない。早期抑止を通過し、第2カメラがない純単眼を前提とする。

| 記号 | 型・意味 |
| --- | --- |
| \(i,l,r\) | 整数のFrame識別番号。順に現在画像、最後にKeyFrame化した画像、保存された最終再局在画像。KeyFrame固有の番号とは区別する |
| \(M,m\) | 整数の画像数。`mMaxFrames`と`mMinFrames`。現行設定経路では\(m=0\)、\(M\)は設定側FPS由来 |
| \(K\) | 現在地図のKeyFrame数。0以上の整数 |
| \(n\) | 現在の局所追跡で採用した対応位置数。A11の`mnMatchesInliers`で、0以上の整数、単位は個 |
| \(n_{\rm ref}\) | 参照KeyFrameの対象対応位置数。空でなく無効でもないMapPoint参照のうち、登録観測数の条件を満たす数。0以上の整数、単位は個 |
| \(a\) | `AcceptKeyFrames()`から読み取った受付フラグ。型は真/偽 |

\(n_{\rm ref}\)の最低登録観測数は、地図のKeyFrame数\(K\le2\)なら2、それ以外は3である。参照画像の特徴総数ではない。また、\(n\)と\(n_{\rm ref}\)は異なる条件で数えるため、その比を二画像の共通点の厳密な重複率とはみなさない。

候補条件を\(C\)とすると、純単眼では次の形になる。

\[
C=\bigl[(i\ge l+M)\lor((i\ge l+m)\land a)\bigr]
\land(n<0.9n_{\rm ref})\land(n>15).
\]

\(C\)は真/偽、\(\lor\)は「いずれか」、\(\land\)は「両方」を表す。画像番号・個数に空間の次元はなく、比率0.9は無次元である。FPSはFrames Per Second、1秒当たりの画像数で、\(M\)には動画読込側ではなく設定側の値を使う。現行設定の\(M\)は30画像である（`mini3_calib/out/mini3.yaml:22`）。

この式は、画像間隔と受付に関する左側の条件に加え、参照側に比べて現在の採用対応が少なく、かつ15を超える対応が残ることを要求する。観測の変化と最低限の対応を両方見る目安であり、画像内容の新規性を証明する式ではない。

画像間隔の比較は`>=`、対応数の比較は厳密な`<`と`>`である。最大間隔の条件が真でも点数条件は必要なので、30画像ごとに必ず追加する仕組みではない。

## 受付確認から生成・キュー挿入へ

候補条件だけで直ちに生成するのではなく、次の順序で進む。

| 段階 | 条件と処理 |
| --- | --- |
| 必要判定の受付確認 | \(C\)が真なら、保存済み受付フラグ\(a\)または`IsInitializing()`が真の場合に必要判定を真とする |
| どちらも偽の場合 | BAの中断を要求し、純単眼では必要判定を偽にする。他のセンサー用のキュー件数条件は使わない |
| 生成側の入口 | `CreateNewKeyFrame`にも初期化中に関する抑止と`SetNotStop(true)`の成否確認があり、必要判定が真でも早期returnし得る |
| KeyFrame生成 | 現在FrameからKeyFrameを作り、参照KeyFrameを更新し、前後のKeyFrameを結ぶ |
| キューへの受渡し | `InsertKeyFrame`でLocalMappingのリストへ追加し、停止防止設定を解除して、最後にKeyFrame化したFrame番号と参照を更新する |

BAはBundle Adjustmentで、姿勢や地図点を投影誤差に合わせて調整する処理を指す。ここでの中断はその要求フラグを立てることであり、中断の完了を待つ処理とは限らない。

`AcceptKeyFrames`は受付フラグを読む関数であり、名前にかかわらずLocalMappingが厳密に待機中、またはキューが空であることの証明ではない。条件は順次読み取るため、全ての並行処理の状態を同じ瞬間に固定した判定でもない。生成側の追加確認も区別する必要がある。

生成時の`IsInitializing()`が真、かつ地図群を管理するAtlasの慣性初期化が未成立なら入口で戻る。本章の純単眼では慣性初期化を使わない。また`SetNotStop(true)`はLocalMappingが停止済みなら失敗する。通過した場合の停止防止設定は、キューへ渡した後に解除する。

KeyFrame構築では、Frame由来の画像番号・時刻・特徴・記述子・既存MapPoint参照を受け、現在姿勢を設定する。既存MapPointへの参照を渡すことと、地図点の座標を複製して新しい点を作ることは異なる。また、この時点の対応が全てインライア、すなわち姿勢に整合すると判定した観測だけだとは言えない。

純単眼は`CreateNewKeyFrame`の深度から新MapPointを作る分岐へ入らず、キュー挿入へ進む。`InsertKeyFrame`は保護されたリストに追加し、BA中断要求も立てる。この呼出しが戻っても、LocalMappingでの地図更新・最適化が完了したことにはならない。

## 境界の例、限界と出典

早期抑止を通過し、\(n_{\rm ref}=100\)、\(n=80\)、受付が真、\(i\ge l\)とする。現行の\(m=0\)では受付を使う間隔条件が真となり、\(80<90\)かつ\(80>15\)なので候補になる。それでも実際の生成には`bOK`と生成側の条件が必要である。

同じ参照数で\(n=90\)なら厳密な`<90`を満たさず候補にならない。\(n=15\)なら`>15`を満たさない。受付が偽でも最大間隔を満たせば候補条件は成立し得るが、初期化中でもなければ中断要求を出して必要判定は偽となる。これらは判定の説明用の仮定で、実動画の選択頻度を測定したものではない。

[公式Tracking.cc](https://raw.githubusercontent.com/UZ-SLAMLab/ORB_SLAM3/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc)と[公式LocalMapping.cc](https://raw.githubusercontent.com/UZ-SLAMLab/ORB_SLAM3/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/LocalMapping.cc)の固定版を照合した。[ORB-SLAM原論文](https://arxiv.org/pdf/1502.00956v2)のPDF8頁＝誌面7頁・V.Eを本文と画像で再読した。旧論文の20画像超や50点以上という条件を現行値として転記せず、現行の設定由来の間隔、地図規模付き抑止、`>15`、忙しい純単眼の処理をコードで確認した。詳細は [A13調査メモ](../research/A13_evidence.md)。

実動画での追加頻度や並行処理のタイミングは未測定である。キューに渡した後の処理はP02へ、喪失後の経路はA14以降へ接続する。

## 理解確認

1. 追跡が成功した画像は全てKeyFrameになるか。
2. 最大画像間隔を満たせば、点数条件が偽でも必ず追加するか。
3. `InsertKeyFrame`から戻れば、そのKeyFrameの地図処理も完了しているか。

答えの要点：ならない／点数条件も必要／キュー受渡しであり、処理完了とは異なる。
