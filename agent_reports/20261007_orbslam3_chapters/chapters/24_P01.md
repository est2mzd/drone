# P01 Trackingの統括と実行境界

## 図の位置、背景と目的

並行図・データフロー図の **[Tracking]** と、境界図の **[自前ラッパー・ORB-SLAM3本体]** に対応する。**A03からA04〜A22を統括し、必要なKeyFrameをD09からP02へ渡す**位置である。対象は現行wrapperの純単眼・通常SLAMである。

SLAMはSimultaneous Localization and Mapping、自己位置推定と地図作成を同時に行う処理を指す。Trackingは入力画像から姿勢と状態を更新し、地図に残す画像を選ぶ担当である。ただし、担当部品が分かれていることと、別の実行スレッドがあることは同じではない。

本章の目的は、画像一枚の呼出しで同期実行する範囲と、別スレッドへ仕事を渡す境界を理解することである。各算法の導出はA章を参照し、ここでは入力・呼出し・共有情報・戻り値を結び付ける。

## どのスレッドで動くか

現行wrapperの`main`は、画像を読んだ同じスレッドで`System::TrackMonocular`を呼ぶ。その中から`Tracking::GrabImageMonocular`、さらに`Tracking::Track`を直接呼ぶ。wrapperが次の画像の`read`へ進むのは、この呼出しが戻った後である。

```text
[wrapper/main と同じ呼出しスレッド]
画像read -> System::TrackMonocular
              -> Tracking::GrabImageMonocular [Frame構築]
                  -> Tracking::Track
         <- Tcw がwrapperへ戻る

[別スレッドへの受渡し]
Tracking -- KeyFrame待ち行列 --> LocalMapping::Run
LoopClosing::Runはもう一つの別スレッド
各部品はAtlas/Map・検索索引などを介して情報を共有
```

Systemの構築時、Trackingについてはオブジェクトを`new`で作るだけである。`Tracking thread`というコメントに続き、構築を呼んだ主スレッドで動く旨も書かれている。Tracking専用の`std::thread`を作って画像キューへ送る実装ではない。

一方、LocalMapping（局所地図更新）とLoopClosing（再訪検出など）は、それぞれの`Run`を`new thread`で起動する。現行wrapperはViewerを無効にしているため、条件付きの表示スレッド生成には入らない。P02/P03で扱う内部算法と、本章の実行境界は分けて読む。

## 入力を受け取り、A章の処理へ渡す

| 入力 | 渡す時点と役割 |
| --- | --- |
| D05：画像・時刻 | wrapperが毎画像、画像行列`cv::Mat`と秒単位の時刻を`TrackMonocular`へ渡す。時刻生成はA03参照 |
| D03：カメラ校正・設定 | System構築時に設定ファイルを渡し、Tracking側のカメラや歪み情報などを準備する |
| D04：特徴の辞書 | System構築時に読み込み、Trackingへ参照を渡す。画像検索などに使う辞書を毎画像wrapperで読み直す構造ではない |

`GrabImageMonocular`は画像・時刻に加えて、準備済みの特徴抽出器・辞書・カメラ等を使ってFrameを構築する。Frameは一画像の特徴・時刻・姿勢等を持つ入れ物である。その後の`Track`は現在地図と保持状態を使い、次の担当処理を選ぶ。

| A章の範囲 | Tracking部品内での役割 |
| --- | --- |
| A04 | `GrabImageMonocular`とFrame構築による画像前処理・特徴抽出 |
| A05〜A07 | 初期地図の状態判定と単眼初期化 |
| A08〜A13 | 通常追跡、局所地図による確認、状態反映、KeyFrame選択 |
| A14〜A22 | 再局在化、喪失判断、地図の再準備、初期化への復帰 |

KeyFrameは地図用に残す重要画像である。Frameを作ること、姿勢を受理すること、KeyFrameを採用することは別の段階で、すべての入力画像がKeyFrameになるわけではない。

## 返却される情報と、別スレッドへの受渡し

`GrabImageMonocular`は`Track`後のFrameから姿勢を返す。Systemはその値を受け取り、別の状態用mutex（排他ロック）を使って追跡状態・対応MapPointのポインタ列・特徴点列をSystem側へコピーしてから、姿勢値`Tcw`を返す。MapPointは三次元の地図点である。

`Tcw`は世界座標からカメラ座標への回転と平行移動を表す姿勢変換で、単眼の平行移動は任意尺度である（A09参照）。返却値があることだけで追跡成功とは判断しない。状態判定はA05〜A22の各経路による。

現行wrapperは、この返却された`Tcw`を変数へ保存していない。代わりに`GetTrackingState()`を読み、状態値2の`OK`だった画像数を数える。したがって、ライブラリが返せる情報と、wrapperがその場で利用している情報には違いがある。

通常の追加条件が成立して実際の作成処理へ進む場合、TrackingはKeyFrameをLocalMappingへ渡す。`InsertKeyFrame`は専用mutexの下でポインタを待ち行列へ追加する処理であり、LocalMappingの地図更新完了を待つ戻りではない。初期化時の二KeyFrameはA06、通常の追加判定と早期returnはA13を参照する。

例えば、ある画像からKeyFrameを待ち行列へ入れて`TrackMonocular`が戻っても、LocalMapping側の仕事が残っている場合はあり得る。wrapperは次画像の読込へ進めるが、このreturnを全地図処理の完了通知として扱うことはできない。

## 地図ロックの範囲と共有情報

`Track`は取得した現在Mapを`pCurrentMap`に保持し、1886行でそのMapの`mMutexMapUpdate`をロックする。ロックを持つ`unique_lock`は関数スコープに置かれ、取得後に途中の`return`へ進んだ場合も、関数末尾へ達した場合も自動的に解放される。

画像前処理・特徴抽出とFrame構築は、この地図ロックの取得より前である。ロック対象は**取得時に参照していたMap**であり、途中でAtlasのcurrentが変わることと、ロック対象が自動的に切り替わることは同じではない。

このmutexは、同じmutexを使う地図更新区間との同時アクセスを調整する。Atlas全体・すべてのMapPoint・検索索引・待ち行列や全スレッドを一括して凍結するという意味ではない。Systemは各部品へAtlas・辞書・検索データベースなどの参照を渡し、部品相互の参照も接続している。状態コピー用mutexやKeyFrame待ち行列用mutexも別にある。

## 理解確認

1. 現行wrapperは画像をTracking専用スレッドの待ち行列へ送っているか。
2. Frame構築や特徴抽出も、1886行の地図ロックを取得した後に行うか。
3. `TrackMonocular`のreturnは、LocalMappingへ渡した全KeyFrameの処理完了を意味するか。

答えの要点：mainから同期的に直接呼ぶ／ロック取得前に構築する／受渡しと別スレッド側の処理完了は異なる。
