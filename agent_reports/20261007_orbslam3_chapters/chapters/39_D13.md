# D13 Trackingの姿勢履歴

図の対応：DFD（Data Flow Diagram、データの流れを示す図）の「Trackingの姿勢履歴」。接続は **P01,D08 → A23**。純単眼のTrackingが保持する内部履歴と、後で姿勢を再構成するための関係を扱う。

## 相対姿勢と参照を一緒に残す

地図の最適化では、過去に作ったKeyFrame（キーフレーム、以下KF）の姿勢も更新される。画像処理時の世界姿勢だけを固定して残す代わりに、参照KFとの相対姿勢を保存すると、参照KFの現在姿勢を使って対象画像の姿勢を再構成できる。

履歴追加の入力は、現在Frameの姿勢・参照KF・画像時刻・Tracking状態である。結果は4本のリストへ追加される。これらは次画像の処理や終了時の出力に使われる内部情報で、wrapperが毎回の`TrackMonocular`戻り値を直接保存したものではない（D08）。

| リスト | C++の型 | 同じ追記位置で保持する内容 |
| --- | --- | --- |
| `mlRelativeFramePoses` | `list<Sophus::SE3f>` | 参照KFに対する相対姿勢 |
| `mlpReferences` | `list<KeyFrame*>` | 参照KFへのポインタ |
| `mlFrameTimes` | `list<double>` | 履歴に付ける時刻、単位は秒 |
| `mlbLost` | `list<bool>` | 履歴をlostとして扱うための印 |

同じ順番の要素を論理上一組として扱うが、実装は別々のlistである。4要素を一括更新する原子的なレコードではない。各要素に入力Frame ID（Identifier、識別番号）やMap IDを直接保存している形式でもないため、履歴の順番と入力Frame番号を同一視しない。

## 保存する相対変換の向き

利用可能な参照KFと、設定された現在姿勢がある場合の関係は次のとおりである。

\[
T_{cr}=T_{cw}T_{rw}^{-1},\qquad
\widehat T_{cw}=T_{cr}T_{rw}^{\mathrm{now}}.
\]

| 記号 | 型・座標方向・意味 |
| --- | --- |
| \(w,c,r\) | wは所属地図の世界座標、cは対象Frameのカメラ、rはその履歴の参照KFのカメラ |
| \(T_{ab}\) | 座標bから座標aへの三次元剛体変換。変換先・変換元の順で下添字を付ける |
| \(T_{cw},T_{rw}\) | 履歴を追加するときの世界→対象カメラ、世界→参照カメラの姿勢 |
| \(T_{rw}^{-1}\) | 参照カメラ→世界の逆変換。上付き−1は逆変換の記号 |
| \(T_{cr}\) | 参照カメラ→対象カメラの相対姿勢。これを履歴へ保存する |
| \(T_{rw}^{\mathrm{now}}\) | 読み出す時点の参照KFの世界→カメラ姿勢。nowは現在値の目印 |
| \(\widehat T_{cw}\) | 相対姿勢と現在の参照姿勢から再構成した世界→対象カメラの姿勢。帽子は再構成値の目印 |

各変換は、正規直交・行列式＋1の3×3回転と三成分の並進からなる。回転は無次元、並進は同じ地図の長さ単位で、純単眼では任意尺度である。コードの`SE3f`は単精度浮動小数点の剛体姿勢を扱う型で、時刻ではない。

積は右側から作用する。最初の式では、参照カメラ→世界→対象カメラと進むので、保存値は世界姿勢そのものではなく参照カメラからの変換になる。再構成では、世界→現在の参照カメラ→対象カメラと進む。

`UpdateLastFrame`は運動モデル経路で、履歴末尾の相対姿勢と前Frameの参照KFの現在姿勢を合成する。参照KFの姿勢が補正されれば再構成値も変わり得るが、過去画像の真値を保証する操作ではない。参照が無効化された場合の保存時の扱いはD15へ残す。

## 末尾へ到達した画像だけが追加候補になる

Track末尾の追加部は、状態が`OK`または`RECENTLY_LOST`の場合に入る。それ以前の初期化未成立やLOST処理のreturnでは、この部分まで到達しない。入力一画像につき必ず一履歴、という構造ではない。

| 末尾での条件 | 相対姿勢・参照KF・時刻 | lost印 |
| --- | --- | --- |
| `OK`または`RECENTLY_LOST`、`isSet()==true` | 現在姿勢から相対姿勢を計算し、現在参照と現在画像時刻を追加 | `mState==LOST`の比較結果false |
| 同じ状態条件、`isSet()==false` | それぞれのlistの`back()`、つまり直前値を追加。時刻も直前値 | 同じ比較結果false。直前のlost印のコピーではない |
| 末尾未到達、または外側の状態条件を満たさない | この追加部では追記しない | 追記しない |

`isSet()`はFrameの`mbIsSet`を返す。`SetPose`はこれと`mbHasPose`をtrueにするが、設定済みであることと追跡成立は別である（D06/D08）。else枝は各listに前値が存在することを前提とする操作であり、本章で空list時の安全性や実動画での到達率を検証したものではない。

外側が`OK`または`RECENTLY_LOST`なので、追加時の`mState==LOST`はfalseになる。従って、`RECENTLY_LOST`をtrueと記録する列でも、全入力画像の状態遷移を完全に保存する列でもない。falseだけで、その履歴が高精度の追跡成功を表すと判断しない。

## 三入力の仮定例

履歴が空の状態から、採用レートf＝30画像/秒、入力順k＝0,1,2、画像時刻`t_k=k/f`秒とする。fは有限正値、kは0始まりの整数、t_kは画像に付ける秒値である。下記の枝を通ったと仮定し、実動画で到達を再現した例ではない。

| 入力 | 仮定する処理結果 | 履歴への追加・累計 |
| --- | --- | --- |
| k＝0、0秒 | 初期化候補を準備し、未成立でreturn | なし、0件 |
| k＝1、1/30秒 | 初期化が成立してOK、末尾到達、姿勢設定済み | `(Tcr,参照KF,1/30,false)`を追加、1件 |
| k＝2、2/30秒 | KF数10以下の小地図で初期姿勢推定が失敗しLOST、末尾前にreturn | なし、1件 |

この条件例では入力3件、wrapperが数えるOKは1件、履歴は1件で、時刻列は`[1/30]`秒となる。入力数・OK件数・履歴数は別の量である。

時刻コピーは別の条件例として読む。前値の時刻が1/30秒で、入力時刻2/30秒の処理が`OK/RECENTLY_LOST`かつ`isSet=false`で末尾へ到達したと仮定すれば、追加する時刻も1/30秒となる。相対姿勢と参照も前値を使う一方、lostはその場でfalseを追加する。この枝では履歴に今回の入力時刻が必ず現れるわけではない。

## Map切替とリセットは別の更新

| 操作 | 履歴への現行の作用 |
| --- | --- |
| `CreateMapInAtlas`（A20） | 新Mapを開始するが、この関数に4履歴をclearする処理はない |
| `ResetActiveMap`（A21） | 姿勢・参照・時刻の3履歴をclearせず、lostリストを再構成する |
| 全体の`Reset` | 4リスト全てをclearする |

ActiveResetは、走査用indexが`mnInitialFrameId`未満の要素では旧lost値を残し、それ以外をtrueにする。indexは初期値と残るMapの情報から設定し、各要素ごとに一つ増やす実装である。各履歴の実Frame IDや所属Mapを直接読み取って選別する処理ではないため、「対象Mapの履歴を正確に全件選別する」とは断定しない。

この後書換えがあることも、lost印を画像入力時の状態ログと区別する理由である。Map切替後に旧履歴が残ることと、それを保存時に全て同じ条件で出力できることも別である。出力列や参照をたどる詳細はD15で扱う。

## 理解確認

1. 相対姿勢Tcrは、どこからどこへの変換か。
2. `isSet=false`の枝では時刻とlost印をそれぞれどこから得るか。
3. 入力数・履歴数・OK件数と、全Reset・ActiveResetの作用を同一視してよいか。

答えの要点：参照KFカメラ→対象カメラ／時刻はback、lostはその場の比較でfalse／それぞれ生成条件・処理が異なる。
