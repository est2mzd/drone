# A04 グレー化と特徴抽出

## 図の位置と目的

図Aの **[画像中の目印を取り出す]**、データフロー図の **[グレー化・特徴抽出]** に対応する。D05の画像・時刻とD03の校正を受け、特徴を持つD06のFrameを作ってA05へ進む。

背景にある問題は、次の画像で「前にも見た場所」を探すための比較材料が必要なことである。画像全体を一つの模様として扱う代わりに、局所的な目印とその見た目を取り出す。

目的は、**画像上の位置を表す特徴点と、見た目を比較する記述子を作ること**。ORB（Oriented FAST and Rotated BRIEF）は、目印の検出に向きと縮尺への対応を加え、短いビット列で見た目を記述する方式である。この段階だけで3次元位置を求めるわけではない。

## 入出力と全体の流れ

| 入出力 | この段階での意味 |
| --- | --- |
| 入力画像・時刻 | 一枚の画素配列と、その画像に付いた時間ラベル。時刻はFrameへ引き継ぐ |
| 校正・抽出設定 | 特徴点座標の歪み補正、抽出数の要求値、画像の段数などに使う |
| 特徴点 | 2次元の画素位置、縮小画像の段、向きなど。Frameの`mvKeys`へ入る |
| 記述子 | 特徴点ごとの256ビット列。`mDescriptors`では1点につき32バイト |
| 補正後の特徴点 | 必要な座標補正をした点を`mvKeysUn`へ保持する |

```text
画像 → グレー化 → 縮尺の異なる画像の列 → 候補検出と分布調整
                                           ↓
                   Frame ← 記述子作成 ← 向きの推定
                     ↓
            特徴点座標の歪み補正 → A05
```

この図の「歪み補正」は特徴点の座標に対する処理である。現行単眼経路では、画像全面を先に歪み補正してから特徴抽出する流れとして説明してはいけない。記述子は補正前の画像に基づいて作り、補正後の点座標は幾何計算のために別に持つ。

## 理論1：グレー画像と画像ピラミッド

グレー化は、色の複数成分から明るさを表す1成分へ変換する処理である。手元の抽出器は8ビット・単チャネル画像を要求する。以後の「輝度値」は0〜255の画像の値であり、物理的な明るさを校正した測定値ではない。

同じ目印でも近づけば大きく写るため、元画像を段階的に縮小した**画像ピラミッド**を作り、各段で特徴を探す。手元の倍率と点座標の戻し方を整理すると、次のようになる。

\[
s_\ell=a^\ell,\qquad \mathbf p_0\approx s_\ell\mathbf p_\ell.
\]

\(\ell\)は0始まりの段番号、\(a>1\)は段間の倍率、\(s_\ell\)は元画像に対する倍率で、どちらも無次元である。\(\mathbf p_\ell=(u_\ell,v_\ell)^T\)は第\(\ell\)段の2次元画素座標、\(\mathbf p_0\)は元画像の画素座標。原点は各画像の左上、右が正の横方向、下が正の縦方向で、単位は各画像の画素である。

コードは抽出点に倍率を掛けて元画像の座標へ戻す。上式の近似記号は、画像サイズの整数丸めや画素値の補間まで含めた厳密な連続画像の対応ではないことを表す。現行設定は倍率1.2、8段である。

## 理論2：角らしい候補を検出し、画面内に分布させる

FAST（Features from Accelerated Segment Test）は、候補点の周囲の環に沿う画素と中心画素の明るさを比べる。連続した画素が中心よりしきい値を超えて明るい、または暗いといった条件から、角らしい候補を高速に探す。環上の全画素が同じである必要はない。[OpenCV公式FAST解説](https://docs.opencv.org/4.13.0/df/d0c/tutorial_py_fast.html)

手元では各段を小領域に区切り、FASTの候補が空の小領域だけ低いしきい値で再試行する。その後`DistributeOctTree`が領域を分割して分布を調整し、末端領域の候補から応答値が最大の点を残す。特定の細かい模様に特徴が集中するのを抑えるための選別であり、3次元空間の地図を分割する処理ではない。

原論文2頁§3.1はHarrisという角らしさの評価値による上位選別を説明する。一方、現行コードが呼ぶのは`ComputeKeyPointsOctTree`で、Harris応答の再計算はない。`ComputeKeyPointsOld`の呼出しはコメントになっている。原論文の全手順を、そのまま手元の処理だと読み替えない。[ORB原論文][orb-paper]。OpenCV（Open Source Computer Vision Library：画像処理のライブラリ）の[公式ORB解説](https://docs.opencv.org/4.13.0/d1/d89/tutorial_py_orb.html)にもHarrisの説明がある。

## 理論3：明るさの偏りから向きを付ける

画像が回転しても周囲の同じ模様を比べられるよう、各特徴点に局所的な向きを付ける。手元の`IC_Angle`が計算する量を、次の整理式で表す。

\[
m_{10}=\sum_{(x,y)\in\Omega}xJ(x,y),\quad
m_{01}=\sum_{(x,y)\in\Omega}yJ(x,y),\quad
\theta=\operatorname{atan2}(m_{01},m_{10}).
\]

\(\Omega\)は特徴点を中心とする円形の整数画素近傍。\(x,y\)はその中心からの横・縦のずれで、右・下を正とし、単位はそのピラミッド段の画素。\(J(x,y)\)は近傍の輝度値、\(m_{10},m_{01}\)は輝度で重み付けした横・縦の和で、単位は画素×輝度値である。手元では半径15画素の円形近傍を使う。

\(\operatorname{atan2}\)は横と縦の二成分から象限を含む方向を求める関数、\(\theta\)はラジアン単位の方向である。この向きは、特徴点中心から明るさの重心へ向かう方向に対応する。コードは重心位置の除算を行わず、二つの和から直接向きを求める。

原論文2頁§3.2の式(1)〜(3)は、モーメントから重心、方向へ進む。本章の記号で重心を書くと、次の式になる。[ORB原論文][orb-paper]

\[
m_{00}=\sum_{(x,y)\in\Omega}J(x,y),\qquad
\mathbf C=\left(\frac{m_{10}}{m_{00}},\frac{m_{01}}{m_{00}}\right).
\]

\(m_{00}\)は輝度値の総和、\(\mathbf C\)は特徴点中心に対する重心の2次元画素座標である。\(m_{00}>0\)なら両成分を同じ正数で割っても向きは変わらないため、手元コードのように除算を省いて方向を求められる。これは方向式との対応であり、コードが重心座標を明示的に保存するという意味ではない。

理論上の向きには、二つの和がともに0ではない前提がある。値が小さいと、雑音で方向が大きく変わり得る。実装の`fastAtan2`は**度**で値を返し、記述子作成時に\(\pi/180\)を掛けてラジアンへ直す。\(\pi\)は円周率で、三角関数の角度単位をそろえる変換である。[OpenCV公式 `fastAtan2`](https://docs.opencv.org/4.13.0/db/de0/group__core__utils.html)

## 理論4：向きに合わせた明暗比較をビットにする

BRIEF（Binary Robust Independent Elementary Features）は、近傍の二つの位置の明暗比較を多数並べて見た目を表す方式である。手元では比較位置の組を特徴点の向きに回転させ、平滑化した画像上で256回比較する。平滑化は小さな明るさの変動をならす処理である。

\[
R_\theta=\begin{pmatrix}\cos\theta&-\sin\theta\\\sin\theta&\cos\theta\end{pmatrix},\qquad
d_i=\mathbf1\!\left[\widetilde I(\mathbf c+\operatorname{round}(R_\theta\mathbf a_i))<
\widetilde I(\mathbf c+\operatorname{round}(R_\theta\mathbf b_i))\right].
\]

\(i=0,\ldots,255\)は比較番号。\(\mathbf a_i,\mathbf b_i\)は固定パターンに保存された2次元の画素オフセット、\(\mathbf c\)は整数へ丸めた特徴点中心で、すべて当該段の右・下を正とする画素座標である。\(R_\theta\)は無次元の2×2回転行列。画像の縦軸が下向きなので、正の角度は画面上で時計回りに見える。

\(\operatorname{round}\)は各成分を整数画素へ丸める操作で、コードの`cvRound`に対応する。\(\widetilde I\)は当該段を平滑化した輝度画像、\(\mathbf1[条件]\)は条件が真なら1、偽なら0を返す記号。\(d_i\)は単位のない0/1の値で、256個を並べたものが記述子である。画素値が等しい比較は0になる。

原論文3頁§4.1の式(4)は輝度比較、式(5)はビット列の表現、式(6)は回転した比較位置を使う記述子を示す。本章の式は画素丸めまで展開した手元実装の整理式であり、原論文の式そのものではない。[ORB原論文][orb-paper]

同節の実装記述は12度刻みの参照表と、積分画像を使う5×5小窓の平滑化である。積分画像は矩形内の画素値の和を速く計算するための累積表を指す。手元コードは記述用画像へ7×7のガウス平滑化を行い、角度から三角関数で回転を計算して`cvRound`する。12度刻みの選択はなくても、浮動小数演算と画素丸めは含む。向きの計算と記述用画像の平滑化は別の段階である。[ORB原論文、3頁§4.1][orb-paper]

## 現行コードと抽出数

確認日2026-10-07、ORB_SLAM3 HEAD `4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4`。下記のTracking・Frame・ORBextractorは既存差分なし。パスはすべて`third_party/ORB_SLAM3/src/`を先頭に付ける。

| ファイル・関数・行 | 本章との対応 |
| --- | --- |
| `Tracking.cc:1566-1589` `GrabImageMonocular` | 色順設定に従ってグレー化し、抽出器を選んでFrameを生成 |
| `Tracking.cc:588-601` `newParameterLoader` | 通常は`nFeatures`、初期用は`5*nFeatures`で抽出器を準備 |
| `ORBextractor.cc:1086-1138,1170-1186` `operator()` / `ComputePyramid` | 型確認、画像の段、候補、記述子作成の順 |
| `ORBextractor.cc:781-895,757-775` `ComputeKeyPointsOctTree` / `DistributeOctTree` | FAST候補と分布調整、方向計算への接続 |
| `ORBextractor.cc:76-142` `IC_Angle` / `computeOrbDescriptor` | 方向の二つの和、度からラジアンへの変換、32バイトの比較結果 |
| `Frame.cc:307-330,747-778` 単眼コンストラクタ / `UndistortKeyPoints` | 抽出後に点座標を補正。MapPointとの対応欄をNULLで初期化 |

現行設定の要求値は通常1000、初期用5000である。初期用は初期状態に加え、`GrabImageMonocular`内のID差条件`lastID-initID < mMaxFrames`が成立したときにも選ばれる。画像中の候補と選別結果によって実数は変わるため、常に1000点や5000点を得る保証ではない。

Frameは抽出数を`mvKeys.size()`から受け取る。0点なら後続の点補正等を行う前に戻る。特徴点に対応するMapPoint（複数観測から求める3次元地図点）の欄は、この段階ではNULL、つまり対応なしである。

## 具体例、成立条件と限界

平滑化画像である比較組の値が30と70なら、そのビットは1になる。順が70と30なら0である。このような比較を256個並べると32バイトになるが、その列だけに奥行きや実寸は入っていない。別画像との比較ではビットの相違数を使えるものの、似ているだけで同じ3次元点と確定するわけではない。

模様の少なさ、ぼけ、照明の変化、遮蔽などで候補や記述が不安定になり得る。画像ピラミッドと方向付けも、あらゆる縮尺・回転・視点変化に対する成功を保証しない。今回、実動画の抽出点数や性能を測定してはいない。
