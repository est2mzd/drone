# O03 patrolの別系統への接続

図の対応：境界図の「patrol：別の特徴地図・PnP等」。接続は **D01,D15 → 別の特徴地図・姿勢・巡回研究**。保存動画と姿勢を使う位置推定、および巡回研究への接続を扱う。

## 保存された姿勢から別の特徴地図を作る

SLAM（Simultaneous Localization and Mapping、自己位置推定と地図作成）の推定結果は、別プログラムが画像の位置を求めるためにも利用できる。現行`patrol`は保存動画・D15の姿勢・校正を読み、画像間の対応から三次元点を新たに作り、その点と記述子を保存する。後で問い合わせ画像を照合し、保存地図に対するカメラ姿勢を求める。

この地図は、ORB-SLAM3のAtlasを再読込したものではない。内部のMapPoint参照、共視関係、BoW（Bag of Words、特徴を語彙へ集約した画像表現）検索用データベースを引き継ぐ経路でもない。入力にD14の地図点ファイルを要求せず、三次元点は`patrol/localization.py`が作る。

| 段階 | 主な入出力 |
| --- | --- |
| `patrol.cli build-map` | 動画・姿勢・校正 → `localization.build_map` → 圧縮NPZ形式の配列ファイル |
| `Localizer.estimate` | 保存配列と問い合わせ画像 → 3D–2D対応 → 姿勢、valid、対応数、画素残差 |
| `patrol.cli demo` | 動画上の位置推定と、別の合成地図での巡回 → 表示動画・ログ |
| `runtime.Alignment/PatrolRuntime` | 外部から与える尺度・座標対応・時刻・不確かさ等 → 機体位置への変換と速度の提案 |

NPZはNumPyの配列群を一つのファイルに保存する形式である。特徴地図と、巡回に使うメートル単位の障害物・確認済み空間の地図は、用途も保存内容も異なる。

## D15の姿勢ファイルにも追加の入力条件がある

`build_map`は9列` t tx ty tz qx qy qz qw valid `を要求し、**全行・全列が有限値で、時刻が厳密に増加すること**をvalid選別前に検査する。D15は履歴によって前値の時刻をコピーし得るため、D15で保存できたファイルが必ずそのまま受理されるとは限らない。重複時刻もこの入口では拒否する。

採用対象はvalidが1の行で、既定では前の採用から1秒以上空ける。各姿勢時刻と動画FPS（Frames Per Second、秒当たりの画像枚数）から`round(t*fps)`の画像番号を求め、動画を読む。CLI（Command Line Interface、コマンドによる入口）の参照終了時刻は既定35秒であり、その時刻未満を候補にする。

姿勢のクォータニオンは有限性・ノルムを確認して正規化し、3×3回転Rと三成分並進tから世界→カメラの3×4行列`[R|t]`を組み立てる。回転は無次元、並進は保存地図と同じ任意長さ単位であり、並進列をカメラ中心と混同しない（D15）。校正はCamera1の内部行列と5歪み係数を使う。

## 画像の特徴を三次元点へ結び付ける

各参照画像から、OpenCVのORB（Oriented FAST and Rotated BRIEF、A04の方向付き二進特徴）を抽出する。FASTはFeatures from Accelerated Segment Testという検出法、BRIEFはBinary Robust Independent Elementary Featuresという二進記述方式を指す。

| 順序 | 現行処理と意味 |
| --- | --- |
| 1 | 参照画像ごとに、2秒以上先にある最初の参照画像を相手に選ぶ |
| 2 | Hamming距離、二近傍の距離比、距離上限で記述子の対応を選ぶ |
| 3 | `undistortPoints`で歪みを除いた正規化座標を得る。ここではPを指定しないため、D03のFrameの補正後画素とは出力座標が異なる |
| 4 | 二つの保存Tcwと正規化座標を`triangulatePoints`へ渡し、同次座標から三次元位置を求める |
| 5 | 有限性、両カメラでの正深度、再投影誤差、視差で選別し、点と最初の参照側の記述子を保存する |

1秒・2秒は画像を選ぶ時間間隔であり、カメラが何メートル動いたかを保証する値ではない。例えば1秒と3秒の姿勢があっても、同じ場所で向きを変えただけなら、その時間差だけで安定な奥行きは得られない。正規化座標と投影行列の整合、視差の役割はA06/D03を参照する。

一回の照合では`trainIdx`を一意にするが、異なる画像ペアで同じ物理点を復元した結果を、地図全体で統合する処理ではない。保存レコード数を、現実の異なる点の数と無条件に読み替えない。

保存内容は`xyz`、`descriptors`、内部行列`k`、歪み`d`、各点を作った二参照時刻`reference_times`、`units='slam_units'`、`pose_convention='Tcw'`等である。`Localizer`は配列を読み、問い合わせごとに姿勢を推定する。この経路でAtlasへ点を追加したり、語彙を学習・更新したりするわけではない。

## 問い合わせ画像からPnPで姿勢を求める

PnP（Perspective-n-Point）は、既知の三次元点と画像上の二次元点の対応からカメラ姿勢を求める処理である。`estimate`は問い合わせのORB記述子を保存記述子に照合し、その添字で三次元位置を引く。

現行の呼出しは`solvePnPRansac(..., SOLVEPNP_EPNP)`である。RANSAC（Random Sample Consensus）は外れ値を含む対応から仮説を試す方法、EPnP（Efficient Perspective-n-Point）はここで指定する姿勢計算法である。返されたインライア集合に対し、LM（Levenberg–Marquardt）法の`solvePnPRefineLM`で姿勢を改善する。A15の本体側の最尤法に基づく姿勢ソルバとは別の呼出しである。

本章ではSLAM世界座標をs、問い合わせカメラをcとし、次の関係で整理する。コードの`rotation_cw`が表す回転を、ここでは座標の区別のためRcsと記す。

\[
u_j\simeq\pi_{K,D}(R_{cs}P_j+t_{cs}),\qquad
C_s=-R_{cs}^{\mathsf T}t_{cs}.
\]

| 記号 | 型・単位・座標・前提 |
| --- | --- |
| \(j,P_j\) | jは対応する保存レコードの整数添字。PjはSLAM座標の三成分点、任意長さ単位 |
| \(u_j\) | 問い合わせ画像で検出した二成分画素座標、pixel。右・下が正 |
| \(R_{cs},t_{cs}\) | SLAM座標→カメラの3×3回転と三成分並進。回転は正規直交・行列式＋1・無次元、並進はPjと同じ単位 |
| \(K,D\) | 3×3内部行列と5成分歪み係数。焦点距離・主点はpixel、歪み係数は無次元 |
| \(\pi_{K,D}\) | 三成分カメラ座標を透視除算・歪み・内部行列により二成分画素へ写す関数。正の前方深度を前提とする |
| \(C_s,\mathsf T,\simeq\) | Csはカメラ中心、三成分・SLAM長さ単位。上付きTは転置、近似記号は観測誤差を含む対応であることを示す |

点と姿勢の座標系、画像と校正が整合し、有限で有効な幾何対応を持つという前提の式である。カメラ軸は右・下・前方。点の位置を固定して姿勢を求めるため、新たな単眼のメートル尺度をこのPnPだけで決めることはない。

コードは対応18件以上、PnPの成否とインライア18件以上を確認する。改善後の再投影RMS（Root Mean Square、二乗平均平方根）が3 pixelを超える、または採用点の深度が非正なら不合格にする。この計数は保存レコードに基づき、前述の物理点の重複統合を保証しない。

結果の`position`はCsで、`rotation_cw`や`rms_px`も返す。ここでのvalidはこの位置推定器の受理結果であり、D15の保存validや本体のTracking状態とは別である。画素RMSをメートルの位置誤差や位置共分散へ直接読み替えない。

## 任意尺度から巡回座標へつなぐ条件

巡回用の`World`はメートル単位、Z上向きの座標で、障害物ボックスと`verified_free`に指定された確認済み空間を使う。疎な特徴点が存在しない場所を、自動的に通行可能とする地図ではない。経路計画はこの別地図上のA*探索などで行う。

`Alignment`のカメラ位置段階は、外部指定された相似変換で次のように表せる。

\[
C_w=\alpha R_{ws}C_s+t_{ws}.
\]

wは巡回用の世界座標。Cwとtwsは三成分で単位m、RwsはSLAM座標→巡回座標の3×3正規直交回転で行列式＋1、無次元である。正の有限な尺度αの単位はm/SLAM単位。例えばCs=`(2,0,0)`、測定値として別途α=0.5、回転なし、並進ゼロを仮定すれば、Cw=`(1,0,0)` mとなる。これは実際の校正値ではない。

`Alignment`は測定済み尺度・外部変換・固定ジンバルの指定を検査するが、自動的に測定する処理ではない。さらにカメラと機体の回転・取付位置を使い、カメラ中心から機体位置へ補正する。カメラ中心をそのまま機体位置とする前提は置かない。

`PatrolRuntime`へは画像と周囲形状の時刻、メートル単位の不確かさ` sigma_m `などを外部から与える。現在のPnPがsigma_mを校正済みの値として生成するわけではない。状態や情報の古さなどを判定する制御コードはあるが、SDK（Software Development Kit、機体用開発ライブラリ）の軸が未確認なら、送信用速度はゼロとして提案速度と分離する。

## 動画評価・合成巡回・実機を区別する

実動画のデモは画像を`Localizer`へ渡し、近い時刻のORB-SLAM3姿勢との位置差をSLAM単位で記録する。既定の35秒の前後による区分は、特徴地図の参照画像と問い合わせを分けるためのものである。元のORB姿勢は動画全体の地図最適化から得られ、比較相手も独立した正解位置ではない。

巡回デモは別の合成地図で、シミュレーションの位置と周囲形状を制御器へ与える。位置喪失や障害物追加を注入し、提案速度で合成位置を進める。実動画PnPの結果をそのまま使って実機を閉ループ巡回した実証ではない。READMEの既存成績を今回再測定したものとしては扱わない。

実機向けのコード境界では、`bridge_cli`はゼロ速度を送る試験経路であり、Androidの`LIVE_OUTPUT_ENABLED`はfalseである。これらの設定やゼロ速度目標は、実機での物理的停止や飛行性能を実証したものではない。本章では全制御仕様や操作手順を扱わない。

## 理解確認

1. patrolの特徴地図は、どの入力から、誰が三次元点を作るか。
2. Cs=`(2,0,0)`というPnP結果を、なぜ2 mの機体位置と即断できないか。
3. ORB姿勢との比較、合成巡回の完了、実機閉ループ飛行は同じ実証か。

答えの要点：動画・保存姿勢・校正からpatrolが別途三角測量／任意尺度とカメラ・機体座標の違いがある／比較基準と入力される位置・地図が異なり、実機飛行は未実証。
