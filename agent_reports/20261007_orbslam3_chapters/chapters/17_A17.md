# A17 復帰試行を続けるかの判断

## 図の位置、背景と目的

図Bの **<まだ復帰を試す?>** に対応する。A16の再局在化が不成立だった側から入り、**はい→合流点Aから次画像へ、いいえ→A18の喪失確定**へ進む。対象は純単眼・通常SLAMで、入口状態が`RECENTLY_LOST`の場合である。SLAMはSimultaneous Localization and Mapping、自己位置推定と地図作成を同時に行う処理を指す。`RECENTLY_LOST`は最近追跡を見失い、既存地図上の位置を探し直す状態である。本章は、今回の試行が失敗した後、いつ喪失確定側へ進むかを説明する。

入力は今回の再局在化関数の成否、現在画像の時刻、保存した喪失開始画像時刻である。出力は、この条件で一時喪失状態を継続するか、`LOST`へ移るかという判断である。`LOST`は喪失が確定した状態を指す。

## 再局在化を先に実行する

現行コードは、まず`bOK=Relocalization()`で今回の画像を使った再局在化を試す。**その後で**画像時刻差と戻り値を調べる。時間差が大きいことを理由に、今回の再局在化を呼ぶ前に打ち切る構造ではない。

\(t_k\)を現在画像の時刻、\(t_{\rm lost}\)を保存された喪失開始時刻、\(b\)を今回の`Relocalization`の戻り値とすると、喪失確定側へ移る条件は次のように整理できる。

\[
\Delta t=t_k-t_{\rm lost},\qquad
L(\Delta t,b)=(\Delta t>3.0\,\mathrm{s})\land\neg b.
\]

\(t_k,t_{\rm lost},\Delta t\)は実数として扱う秒単位の画像時刻とその差、\(k\)は現在画像の順序を示す整数添字である。\(b\)と\(L\)は真/偽、\(\land\)は両条件、\(\neg\)は否定を表す。式はコードの整理で、空間の次元や座標変換を持たない。前提はこの純単眼の一時喪失経路へ到達したことである。

\(L\)が真なら`mState=LOST`とし、`bOK=false`を設定する。図A17へ来る不成立側では\(b\)は偽なので、\(L\)が偽なら図の「はい」、真なら「いいえ」に対応する。参考として今回成功した場合も含めると、境界は次のようになる。

| 比較する画像時刻差と今回の戻り値 | この箇所の動作 |
| --- | --- |
| \(\Delta t\le3.0\)秒、\(b=\mathrm{false}\) | この条件では`LOST`にせず、次画像を試せる状態を保持する |
| \(\Delta t>3.0\)秒、\(b=\mathrm{false}\) | `LOST`へ変更し、A18へ接続する |
| 時刻差にかかわらず\(b=\mathrm{true}\) | この条件は発火しない。図ではA16の成立側からA10へ進む |

比較は厳密な`>`である。計算された差がちょうど3.0秒なら、失敗していてもこの条件は発火しない。また、ここでの\(b\)は後続の`TrackLocalMap`より前の戻り値であり、画像処理全体の最終追跡成功とは異なる。

したがって「3秒以内に最終状態`OK`へ戻れなければ必ず`LOST`になる」という規則ではない。今回の再局在化が真だった後にも、A10の局所地図確認とその結果の反映がある（A16参照）。

## 画像時刻であり、実時間の待機ではない

保存元は現在Frameの`mTimeStamp`である。Frameは一画像の特徴・時刻等を持つ入れ物を指す。このwrapper（自前の呼出しプログラム）では、A03のとおり時刻 \(t_k=k/f\) を渡す。

ここでは\(k\)は読めた画像の0始まり番号、\(f\)は動画読込側のFPSである。FPSはFrames Per Second、1秒当たりの画像数で、単位は画像/秒、式は有効な正の\(f\)を前提とする。喪失開始時刻も同じ入力画像の時間基準から保存される。

これは処理開始からの時計経過や、一画像を処理するのに要した時間ではない。この分岐が3秒間スリープして待つわけでもない。動画を速く処理しても遅く処理しても、判定へ渡す時刻は画像番号とFPSから決まる。

次画像で再試行するには、画像入力が続き、対象状態で再びこの枝へ入る必要がある。動画終端・読込失敗でwrapperのループが終われば、画像が来ない間に独立した時計がこの判定を進める仕組みではない。

`time_recently_lost`という変数の初期値5.0は、慣性付き入力側の別分岐で使われる。本章の純単眼経路は直接`3.0f`と比較しており、変数名だけから純単眼にも5秒を適用しない。

## 現行コード、境界例と限界

確認日2026-10-07、ORB_SLAM3 HEAD `4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4`。`Tracking.cc`は`third_party/ORB_SLAM3/src/`以下。

| ファイル・関数・行 | 本章の対応 |
| --- | --- |
| `Tracking.cc:2000-2011` `Track` | 再局在化の先行、厳密な時刻差と戻り値の条件 |
| 同`:1970,2162` | 喪失開始値へ入力画像時刻を保存 |
| 同`:48,1986-1997` | 慣性付き入力で使う5.0の変数と別分岐 |
| `slam/src/offline_mono.cpp:33-47,54` | 動画FPSと画像番号による時刻、画像読込ループ |

例えば比較時の時刻差が3.0秒で今回の戻り値が偽なら条件不成立、3.1秒で偽なら成立、3.1秒でも真なら不成立である。これらは比較へ入る数値を仮定した例であり、撮像時刻の真値や浮動小数点の丸め誤差を測定した例ではない。

本章の条件は実装上の遷移規則であり、現実の時計で何秒以内に復帰するか、復帰率がどれほどかを保証しない。実動画の遷移回数は未測定である。条件成立後の状態確定と同じ画像の後続処理はA18へ接続する。

[固定コミットの公式Tracking.cc](https://raw.githubusercontent.com/UZ-SLAMLab/ORB_SLAM3/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc)を照合し、[ORB-SLAM3論文](https://arxiv.org/pdf/2007.11898v2)のPDF5頁・§IIIのTracking喪失説明を本文と画像で再読した。論文の期間を設けて復帰を試す概説と、現行の3.0・等号境界・成功条件付きの順序を区別する。詳細は [A17調査メモ](../research/A17_evidence.md)。

## 理解確認

1. 3秒を超えた画像は、再局在化を呼ばずに直ちに打ち切るか。
2. 時刻差3.0秒で再局在化が偽なら、この条件は発火するか。
3. ここで測っている時間差は、画像処理に要した実時間か。

答えの要点：今回の再局在化を先に試す／厳密な`>`なので発火しない／入力画像の時刻差である。
