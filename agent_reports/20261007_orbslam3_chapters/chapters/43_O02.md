# O02 mini3_bridgeと入力境界

図の対応：境界図の「mini3_bridge・映像転送保存」。接続は **機体映像 → D01**。機体の映像が保存動画となり、後でオフラインのSLAM（Simultaneous Localization and Mapping、自己位置推定と地図作成）へ渡る境界を扱う。

## 映像を運ぶ段階と画像を推定する段階

READMEの運用経路は、DJI Mini 3から送信機RC-N1を経てAndroidへ映像を受け、同じ無線ネットワークのPC（Personal Computer）へ転送する構成である。送信機とAndroidはUSB（Universal Serial Bus）で接続する。今回、実機接続の成立や映像品質を確認したわけではない。

AndroidアプリはDJI Mobile SDK（Software Development Kit、開発用ライブラリ）を使う。Gradleに指定された依存はMobile SDK V5の5.18.0であり、参照用に置かれた公式サンプルツリーの版とは別である。本章で直接追うのは、そのSDKの映像コールバック以降の自前コードである。

```text
Mini 3 → RC-N1 → AndroidのSDK映像コールバック
                    ↓ 圧縮バイト列を独自メッセージ化
             TCP → PC受信 → 圧縮ストリーム保存 → MP4へ格納
                                                  ↓ 別段階
                      offline_mono → OpenCVで復号 → 画像と相対時刻 → SLAM
```

TCP（Transmission Control Protocol）はAndroidとPCの接続に使う通信方式である。ここで転送するのは符号化映像のバイト列であり、SLAMが特徴を検出する画素配列ではない。通信を受けたこと、動画が保存されたこと、画像として復号できたこと、追跡が成立したことは別々の段階になる。

## Androidで何を受けて送るか

`MainActivity`は`StreamForwarder`を生成し、転送開始操作で接続先を渡す。SDKの登録・接続状態は`SdkController`が扱う。SDK登録や製品接続のコールバックがあることを、全フレームの取得成功とは読み替えない。

`StreamForwarder`は利用可能なカメラから`LEFT_OR_MAIN`を優先し、なければ先頭候補を選ぶ。`ReceiveStreamListener`を登録すると、データ配列・開始位置offset・長さlength・ストリーム情報が渡される。自前コードは該当範囲をコピーし、映像形式名、幅、高さを取り出して送る。

これはSDKの圧縮映像ストリームを受け取る経路であり、復号済み`cv::Mat`を受け取る経路ではない。自前の転送処理に画素画像を再エンコードする段階もない。コールバック一回のチャンクを、完全な復号画像一枚と無条件に数えない。

READMEには1280×720のH.264という利用記録があるが、現行コードは受け取った形式・寸法を読む。今回の機体が必ずその条件で配信しているとは未測定である。PC側は形式名からH.264またはH.265/HEVC（High Efficiency Video Coding）用の入力形式を選ぶ。

## 独自メッセージの最小構造

送信側の`frame`と受信側の`read_exact`・長さ解析が対応する。複数の受信操作で必要なバイト数を集めるので、ソケットの一回の`recv`が独自メッセージ一個に一致する前提ではない。

| 部分 | バイト列上の内容 |
| --- | --- |
| 先頭4 byte | 本文長。big-endian、すなわち上位バイトから格納 |
| 本文先頭1 byte | type。1なら形式情報、2なら映像チャンク |
| type 1のpayload | 形式名のバイト長1 byte、UTF-8の形式名、幅・高さが各2 byte |
| type 2のpayload | SDKからコピーした符号化映像のバイト列 |

UTF-8（8-bit Unicode Transformation Format）は文字列をバイト列にする符号化方式である。形式名はSDKの`info.mimeType.name`から取得する列挙値名である。ここでの独自本文長をL、payloadをバイト列Pと書けば、次の関係になる。

\[
L=1+|P|,\qquad \text{メッセージ全体のバイト数}=4+L.
\]

Lはtypeを含む本文の整数バイト数、\(|P|\)はPのバイト数で、縦棒はこの列の長さを表す。先頭4 byte自体はLに含まない。例えばtype 2のpayloadが1000 byteなら、本文長1001 byte、全体1005 byteである。これは説明用の長さで、映像一枚のサイズではない。

受信側は本文長を1以上8,000,000以下として検査する。ただしこの形式には、撮像時刻、独自の連番、フレーム到達確認を表すフィールドがない。長さの検査を、映像の完全性や時刻同期の検証とは扱わない。

## 待ち行列と欠落の境界

Android側の送信待ちキューは容量8である。映像チャンクを追加できなかった場合、待機中の内容をclearして、新しいチャンクを再投入する。このためTCPを使っていても、アプリ内で破棄したデータまで後から自動的に復元できるわけではない。

形式情報のキュー投入結果も検査していない。形式名などを「最後に通知した値」として先に更新するため、形式情報が必ず到達する、失敗時に必ず再送されるという保証も置かない。この静的な制約の確認にとどめ、今回は破棄や復号の異常を再現していない。

別の送信スレッドがキューから取り出してソケットへwrite/flushする。`sentChunks`は映像コールバック側で増え、ソケット送信成功数ではない。`sentBytes`も送信側で書き出した量であり、PCが全画像を復号した確認値ではない。表示される件数を、そのまま有効フレーム数や欠落ゼロの証明に使わない。

## PCの通常入口はrecv_play

`scripts/mini3/recv.sh`が起動するのは`mini3_bridge/pc/recv_play.py`である。このプログラムは表示だけでなく、既定では受けたtype 2のpayloadを圧縮ストリームファイルへ書く。`--no-save`なら保存を省く。別途、同じバイト列を`ffplay`の標準入力へ渡して再生する。

ここでいうrawファイルはH.264/H.265の圧縮elementary stream、つまりコンテナに包む前の符号化データである。「raw」という語から未圧縮の画素配列と解釈しない。再生側の復号と、保存側のバイト列書込みは別の役割である。

通常の受信終了後、保存が有効で受信バイトがあれば、`recv_save.py`から読み込んだ`remux`を呼ぶ。指定はFFmpegの`-fflags +genpts -r fps -f fmt -i ... -c copy`であり、再エンコードせずMP4のコンテナへ格納する。MP4は映像データと再生用情報を収めるファイル形式である。

この「再エンコードなし」は、転送前後で欠落がないという意味ではない。途中の例外や不正な長さなど、すべての終了が必ずMP4完成へ進むとも限らない。`recv_save.py`を直接使う受信経路もあるが、通常入口との違いを保つ。任意の画像列出力機能は、現行の保存動画wrapperに必須ではない。

## 撮像時刻とSLAMの相対時刻

SDKのストリーム情報にはフレームレートもあるが、この独自形式が伝えるのは形式名・幅・高さである。PCでMP4化に指定するFPS（Frames Per Second、秒当たりの画像枚数）は受信プログラムの引数で、既定30である。入力側の`-r`は一定レートを仮定して時刻を生成する指定であり、元の撮像間隔を復元した測定ではない。

PCのファイル名に使う日時は命名時の時計、転送量の表示に使う時計は受信量の報告用である。`recv_save`の経過秒数も、各画像の露光・撮像時刻ではない。これらを混ぜて、機体からPCまでの遅延を求めたことにはしない。

保存動画を指定して`scripts/orb_slam3/run.sh`を使う段階で、初めて`offline_mono`の入力になる。wrapperは`VideoCapture.read`で得た復号画像\(I_k\)と、\(t_k=k/f\)を`TrackMonocular`へ渡す（D01/D02/D05）。\(I_k\)はcv::Matの画素配列、kは0始まりの入力順整数、fは採用FPSで単位は枚/秒、\(t_k\)は相対秒である。式ではfが有限の正数で等間隔モデルを表すと仮定する。

例えば、仮に残った三画像の実際の撮像時刻が`0, 1/30, 3/30`秒であっても、wrapperがf=30として三枚を順に読めば、付ける時刻は`0, 1/30, 2/30`秒である。これは欠落と時刻生成の違いを示す仮定例で、実際にどの画像が失われるかを再現した結果ではない。符号化データの欠落が復号画像へ与える影響も、実ストリーム次第である。

## 映像以外の経路と確認範囲

Androidには`PatrolCommandBridge`という別の操縦系入口があるが、ここで示した映像type 1/type 2の処理とは別である。接続状態や制御の情報が存在することだけで、単眼の`TrackMonocular`へ慣性・衛星測位データが渡るわけではない。制御の内部や飛行手順は本章に含めない。

実機接続、アプリ起動、録画、実codec・FPS・寸法・遅延・欠落・保存完全性の測定はしていない。秘密設定・認証ファイルは開かず、認証値・機器識別値・接続先実値は本文と根拠へ収録していない。文書のみ作成し、コード変更・インストール・次章先行なし。

## 理解確認

1. AndroidからPCへ届くtype 2は、SLAMが直接使う画像配列か。
2. TCP、stream copy、sentChunksの表示は、なぜ全画像保存の証明にならないか。
3. PCのファイル名の日時、MP4の時刻、wrapperのk/fは、元の撮像時計と同一か。

答えの要点：符号化バイト列であり後で復号する／送信前の破棄や復号結果の確認とは別／いずれも撮像時計の復元を保証するものではない。
