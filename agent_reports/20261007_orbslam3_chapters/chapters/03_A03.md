# A03 画像読込と時刻付与

## 図の位置

図Aの **[画像を読む・時刻を付ける]** と、データフロー図の **[読込・時刻付与]** に対応する。入力はD01「保存動画」とD02「動画のFPS」、出力はD05「画像・フレーム時刻」で、その組をA04の特徴抽出へ渡す。FPSはFrames Per Secondの略で、1秒当たりの画像数を意味する。

A02の判断で使う`capture.read(frame)`は、画像の取得も同時に行う。したがってA03は、A02の後で同じ画像をもう一度読む活動ではない。取得できた画像へ時刻を付け、本体へ渡すところまでを扱う。

## 背景と目的

画像は「何が見えたか」を表す。一方、画像の順番だけでは、前の画像から何秒経ったかは分からない。画像に時間のラベルを付けることで、観測内容と動画上の時点を一組として扱える。

本章の目的は、**一枚の画像にどの時刻を付けて本体へ渡すのか、その時刻が何を意味するのか**を理解することである。ここでいう時刻は、日時を示す時計の値に限らず、ある起点からの経過秒も含む。

## 入出力と採用する時間モデル

| 項目 | 現行処理での意味 |
| --- | --- |
| 入力画像 | 保存動画から`read`で取得・デコードした画素配列`frame` |
| 入力のレート情報 | 動画入力から取得するFPS |
| 内部の番号 | `frame_index`。0開始で、ループ本体の末尾まで処理するたびに1増える |
| 出力 | `TrackMonocular(frame, timestamp)`へ渡す、画像と秒単位の時刻の組 |

デコードとは圧縮された動画情報から画像を取り出すこと。読込にはOpenCV（Open Source Computer Vision Library：画像・動画処理のライブラリ）を使う。公式文書の`CAP_PROP_FPS`はフレームレートを表すプロパティであり、この値の取得自体が撮像間隔の実測ではない。[OpenCV公式プロパティ文書](https://docs.opencv.org/4.13.0/d4/d15/group__videoio__flags__base.html)

現行ラッパーは、このレートを起動時に一度取得し、画像が等間隔に並ぶとみなして時刻を計算する。画像ごとに記録された撮像時刻やファイル内の個別時刻を取り出して使う処理ではない。

## 必要な式：画像番号を秒へ変える

\[
t_k=\frac{k}{f},\qquad \mathcal{O}_k=(I_k,t_k).
\]

| 記号 | 型・次元・単位 |
| --- | --- |
| \(k\) | 0始まりの読込成功画像番号。0以上の整数で、画像を数える番号。コードでは`frame_index` |
| \(f\) | ラッパーが採用するFPS。実数で、単位は画像枚数/秒。コードでは`double fps` |
| \(t_k\) | 先頭画像を0とした第\(k\)画像の経過秒。実数で、コードでは`double timestamp` |
| \(I_k\) | 第\(k\)画像の画素配列。コードでは`cv::Mat frame`。画像サイズとチャネルを持つ |
| \(\mathcal{O}_k\) | 画像と時刻をまとめた二要素の組。位置や速度を表す数値ベクトルではない |

意味のある等間隔時刻として使う前提は、\(f\)が有限で正の値であり、そのレートで並ぶ画像列とみなせることである。番号を1秒当たりの枚数で割ると、起点からの秒数になる。式は空間位置を変換せず、世界・カメラ・機体の座標系も扱わない。

コードは`frame_index`を`double`へ変換してから割るため、整数除算によって小数部分を切り捨てる計算ではない。この式は自前ラッパーの処理を表したもので、論文に掲載された時刻推定式ではない。

## 現行コードとの対応

確認日2026-10-07。主プロジェクトHEAD `d1265bc35439dd6ca57687ac93c8b3a7310fc681`、ORB_SLAM3 HEAD `4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4`。`offline_mono.cpp`に差分なし。本体の行番号は既存の保存機能追加を含む手元ファイルである。

| ファイル・関数・行 | 何をしているか |
| --- | --- |
| `slam/src/offline_mono.cpp:33-36` `main` | `CAP_PROP_FPS`を取得し、`fps < 1.0`の場合だけ`30.0`へ置き換える |
| 同`:41-47,54` `main` | 画像を取得し、0開始の番号から時刻を計算して本体へ渡す。末尾で番号を増やす |
| `third_party/ORB_SLAM3/src/System.cc:404,471` `System::TrackMonocular` | 画像と`timestamp`を受け取り、`GrabImageMonocular`へ渡す |
| `third_party/ORB_SLAM3/src/Tracking.cc:1566,1584-1589` `Tracking::GrabImageMonocular` | 受け取った時刻を画像とともに`Frame`の生成へ渡す |
| `third_party/ORB_SLAM3/src/Frame.cc:289-291` 単眼`Frame`コンストラクタ | `mTimeStamp`へ時刻を保存する |

中心となる処理は次の2行である。

```cpp
const double timestamp = static_cast<double>(frame_index) / fps; // 46行
slam.TrackMonocular(frame, timestamp);                          // 47行
```

30への置換は、取得値が1未満の場合に処理上使う代替値を選ぶ規則である。実際の動画が30FPSだったと判定する処理ではない。公式文書では、`get`が非対応のプロパティについて0を返す場合も説明されるが、今回の動画でその事象を確認したわけではない。[OpenCV公式 `VideoCapture::get`](https://docs.opencv.org/4.13.0/d8/dfe/classcv_1_1VideoCapture.html)

`fps < 1.0`以外に有限性を確認する処理はない。したがって、非有限値を含むあらゆる不適切な値が30へ直るという保証はない。非有限値が実際の動画・読込実装から返るかは未検証である。

## 具体例と三つの時間の違い

採用FPSが30なら、最初の3画像への時刻は次のようになる。これは計算例で、実測値ではない。

| 画像番号\(k\) | 付ける時刻\(t_k\) |
| --- | --- |
| 0 | 0秒 |
| 1 | 1/30秒 ≈ 0.0333秒 |
| 2 | 2/30秒 ≈ 0.0667秒 |

この時刻は**画像番号から生成した動画上の時間ラベル**である。カメラが実際に露光した撮像時刻でも、PCがその画像を処理した現在時刻でもない。実際の撮像間隔が不均一なら、一つのFPSによる計算値と撮像時点がずれる可能性がある。

`main`は`read`に成功した画像を呼出し順に本体へ渡し、次の読込へ進む。ソース上に画像を間引く分岐や、FPSへ合わせて待機する処理はない。時刻に1/30秒刻みを付けることと、処理を実時間で30回/秒に調整することは別である。本体内部に待機が一切ない、という意味ではない。

また、`main:44,65`の`steady_clock`は処理側の経過時間を測る。対象はループ開始前から終了・保存処理後までであり、画像へ付ける`timestamp`には代入されない。開始前の本体構築時間もこの計測には含まれない。

## 論文との関係、成立条件と限界

ORB（Oriented FAST and Rotated BRIEF：画像の目印を検出し見た目を記述する方式）を用いるSLAM（Simultaneous Localization and Mapping：自己位置推定と地図作成を同時に行う方法）が本体の役割である。論文5頁の図1/III節はFrame入力とTracking（追跡担当）を示すが、このラッパーの番号/FPS式や30への代替処理は説明していない。[論文PDF、5頁](https://arxiv.org/pdf/2007.11898v2)

画像と時刻は同じ観測を指す組として渡す必要がある。ただし今回は実動画のFPS、個別時刻、画像欠落、可変レートを実測していない。OpenCV公式文書は4.13.0を参照し、手元バイナリとの版一致や動画読込の内部実装は未確認である。FPS自体のデータとしての性質はD02で改めて扱う。

## 出典と理解確認

コード照合・公式文書・キャッシュ論文の本文/図の再読記録は [A03調査メモ](../research/A03_evidence.md) に保存した。

1. FPSが30のとき、0番目と2番目の画像には何秒を付けるか。
2. FPSが0と返って30へ置き換えられたことは、実際の撮像が30FPSだった証拠か。
3. PCで1画像の処理に0.1秒かかっても、このコードの生成時刻は処理時間に合わせて変わるか。

答えの要点：0秒と2/30秒／実撮像レートを確かめた証拠ではない／生成時刻は番号と採用FPSで計算するため、それだけでは変わらない。
