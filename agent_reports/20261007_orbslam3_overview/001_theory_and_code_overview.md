# 単眼ORB-SLAM3：理論とコードの全体像

各図のブロックから詳しい章へ進むには、[全45ブロックの対応一覧・進捗](../20261007_orbslam3_chapters/000_progress.md)を参照する。既存図を保持し、重複する処理・データを同じIDへ対応付けている。

## 1. 背景

このプロジェクトでは、Mini 3の映像をAndroid経由でPCへ送り、カメラの位置を知り、最終的には指定位置への移動につなげたい。現在のORB-SLAM3処理は、保存動画からカメラの動きと周囲の地図を推定する部分を担当する。

うまくいかない結果を見ても、どの処理が何を推定しているか分からなければ、改善の考え方を選べない。そこで最初の授業では全体の仕事の分担を押さえる。投影の式、閾値、設定値の調整は後の授業で扱う。

## 2. 目的

読み終えたときに、次の三点を自分の言葉で説明できることを目指す。

1. なぜカメラの位置と地図を一緒に求めるのか。
2. どの処理が毎画像の位置を求め、どの処理が地図を更新するのか。
3. 画像から姿勢・地図ができるまでに、どんなデータが受け渡されるのか。

## 3. 結論

**SLAMは、未知の場所を見ながら「自分の位置」と「周りの地図」を互いに助け合わせて推定する方法である。** 地図があれば画像と照合して位置を探せる。位置が分かれば、見えたものを地図に置ける。最初は両方が分からないため、複数の画像から小さな地図と相対的な位置関係を作って始める。

ORB-SLAM3では、この仕事を主に三つに分担する。

- **Tracking（追跡）**：現在の画像を既存の観測や地図と照合し、カメラの位置と向きを求める。
- **LocalMapping（局所地図作成）**：重要な画像を使い、周辺の地図点を増やし、位置関係を調整する。
- **LoopClosing（再訪による地図修正）**：以前見た場所との関係を確認し、蓄積したずれを修正する。別々に作った地図の統合も担当する。

現行コードの出力は、カメラの姿勢と、画像の目印に対応する疎な3次元地図である。壁・家具の形状が埋まった地図や、機体への移動指令までをこの処理だけで作るわけではない。単眼では実寸の尺度も別途必要になる。

## 4. アクティビティ図：何を、どの順で行うか

この図の矢印は**処理の進行**を表す。`[ ]` は活動、`< >` は判断、矢印の「はい／いいえ」等は判断の結果。`A` は次の画像へ戻る合流点である。図は現行の単眼・通常地図作成モードを学習用に要約しており、ソースの全分岐を列挙するものではない。

```text
 図A：画像ごとの処理

[動画・校正・特徴の辞書を用意する]
                    |
                    v
 A ----------> <次の画像がある?> -- いいえ --> [終了要求・結果保存]
 ^                  |

 |                  v
 |       [画像を読む・時刻を付ける]             自前ラッパー

 |                  v                         ORB-SLAM3本体

 |                  |
 |                  v
 |       <追跡に使える初期地図がある?>

 |          v                          v

 |          |                    | 正常          | 喪失中
 |          v                    v               v

 +--いいえ     はい         [局所地図で確認]      | 図Bへ
 |              |                |
 |              |           <追跡できた?>
 |              |            |         |
 |              |           はい      いいえ --> [喪失状態へ] --> A
 |              v            v

 |                           |
 +---------------------------+

 図B：喪失状態での復帰判断

 [復帰を判断]
      |
      +-- 再局在化を試す状態 --> [既存地図の場所を探す]
      |                               |
      |                          <復帰できた?>
      |                           |         |
      |                          はい      いいえ
      |                           |         |
      |                    [局所地図で確認] <まだ復帰を試す?>
      |                      図Aへ戻る      |          |
      |                                    はい      いいえ
      |                                     |          |
      |                                     A    [喪失を確定] --> A
      |
      +-- 喪失が確定した状態 --> <地図を残せる?>
                                  |          |
                                 はい      いいえ
                                  |          |
                       [既存地図を残し   [現在地図を
                        新地図を開始]    リセット]
                                  |          |
```

再局在化とは「追跡を見失った現在画像が、既存地図のどこに当たるかを探すこと」。手元版では候補を現在の地図に限定する。復帰の余地がある状態と、地図の再開始を選ぶ状態がある。すべての失敗で同じ回数だけ再局在化するわけではなく、地図の育ち具合や失敗段階で分岐が変わる。復帰後も局所地図での確認が必要である。リセットは現在の地図が対象で、Atlas全体を消すという意味ではない。

図Aの初期化は、二つの視点の対応から位置関係と奥行きを復元し、整合を検証する活動である。成立しなければ次の画像で待機・再試行する。Tracking自身が初期キーフレームと初期地図点を作り、それらをまとめて調整する。これを初期のBundle Adjustment（複数画像の見え方に合うよう、カメラ姿勢と地図点を一緒に調整する処理）という。

### 三つの担当は並行して働く

次の図の `==>` はキーフレームをキューへ入れる仕事の受け渡し、`<-->` は共有地図の参照・更新を表す。キューは、受け取る担当が順に処理できるよう仕事をためる入れ物である。毎画像について左から右の完了を順番に待つ流れではない。

```text
 呼出し元で動く              別スレッド                別スレッド
 [Tracking]                 [LocalMapping]            [LoopClosing]
  画像から姿勢を求める       新しい地図点を作る         再訪候補を確認する
  重要な画像を選ぶ  ======>  周辺の位置関係を調整 =====> 同じ地図ならずれを修正
     キーフレームを渡す        キーフレームを渡す        別地図なら統合を検討
       |                           |                          |
       +---------------------------+--------------------------+
                                   |
                                  <--> [共有する地図群：Atlas]
```

スレッドは、並行して仕事を進める実行の単位である。地図を修正するときには停止や排他制御による協調もある。「並行」は互いに無関係に動くという意味ではない。再局在化はTrackingの仕事、再訪による地図全体の修正はLoopClosingの仕事である。図Aの「局所地図で確認」はTracking内の `TrackLocalMap` であり、別スレッドのLocalMappingとは異なる。

## 5. データフロー図：何が作られ、どこで使われるか

ここでは矢印は**データの受け渡し**を表し、処理順や待ち時間は表さない。`( )` は入力・出力のデータ、`[ ]` は処理、`{ }` は複数の処理が使う保存領域である。

```text
 (保存動画) ------> [読込・時刻付与] ----> (画像・フレーム時刻)
                         ^                         |
                         |                         v
                 (動画のFPS)             [グレー化・特徴抽出]
                                                   |
 (校正：画像と視線の対応) --------------------------+
                                                   v
                                   (Frame：時刻・特徴・対応情報)
                                                   |
                                                   v
 (特徴の辞書) ------------------------------> [Tracking]
                                                   ^  |
 {キーフレーム検索用データベース} -- 復帰候補 ------+  +--> (各画像の姿勢・状態)
                                                   |  |
 {Atlas：地図群} <--- 初期地図・観測関係 ------------+  +--> (選ばれたKeyFrame)
      |                                            |              |
      +---------- 地図点・参照画像 -----------------+              v
                                                          [LocalMapping]
                                                                 |
      +<---------- (新しいMapPoint・修正した姿勢・観測関係) --------+
      |                                                          |
      |                                                   (処理したKeyFrame)
      |                                                          |
      |                                                          v
      +<---------- (整合を取り直した地図・統合結果) ------- [LoopClosing]
      |                                                          ^
      +---------------- 地図・キーフレーム ------------------------+
 (特徴の辞書・検索用データベース) ---- 再訪候補の検索 -------------+

 {Atlas} + (Trackingの姿勢履歴)
                  |
                  v
         [このプロジェクトの保存処理]
                  |
                  +--> (時刻付き地図点ファイル)
                  +--> (姿勢・有効フラグのファイル)
                               |
                               v
                         [別の表示ツール]
```

検索用データベースはキーフレームの登録を受けて更新される。図は代表的な入出力を示しており、キューや全ての索引・参照関係は省略している。画像・校正・辞書は別の役割を持つ。校正はカメラの写り方を表し、辞書は画像の特徴をまとめて似た場所を探すために使う。

### データの言葉をそろえる

| 言葉 | この授業での意味 |
| --- | --- |
| SLAM | Simultaneous Localization and Mapping。自己位置推定と地図作成を同時に行うこと |
| 単眼 | 一つのカメラの画像を使うこと。現行ラッパーは慣性センサの測定を入力しない |
| 姿勢（pose） | カメラの位置と向きの組。機体の位置・向きとは区別する |
| 特徴点 | 画像内で再び見つけやすい目印。画像上の位置であり、まだ3次元地図点ではない |
| 記述子 | 目印の見た目を比較するための数値表現 |
| ORB | Oriented FAST and Rotated BRIEF。特徴点を検出し、その見た目を記述する方式。内部のFAST/BRIEF算法は後で扱う |
| Frame | 一枚の画像に対応する時刻・特徴・地図との対応・推定姿勢等の入れ物 |
| KeyFrame（キーフレーム） | 地図作成や後の照合のために残す重要なフレーム。全画像を残すわけではない |
| MapPoint（地図点） | 複数の観測から推定した3次元の目印。家具一個や壁一枚を表すものではない |
| 観測関係 | どのキーフレームのどの特徴が、どの地図点を見たかというつながり |
| Atlas | 複数の地図を管理する入れ物。追跡喪失後の新地図も扱う |
| FPS | Frames Per Second。動画の一秒あたりの画像数 |
| 校正 | カメラの写り方を測ること。地図全体をメートルへ合わせる作業とは別 |

## 7. このプロジェクトの境界

```text
 [mini3_bridge：映像転送・保存]
                |
             保存動画
                v
 [自前ラッパー] --> [ORB-SLAM3本体] --> 点・姿勢ファイル --> [viewer / RViz]
                                               |
                                               +--> [patrol：別の特徴地図・PnP等]

 保存動画 --> [object_map：物体検出・深度・平面の観測実験]
```

`patrol` はORB-SLAM3の内部スレッドではない。保存された姿勢と動画から別の特徴地図を作り、PnP（Perspective-n-Point：既知の3次元点と画像点の対応から姿勢を求める処理）を行う。`object_map` も別系統の実験で、今回説明したORB-SLAM3の地図更新へ接続した処理ではない。

根拠：`patrol/localization.py:86` `build_map`、`:138` `estimate`、`object_map/extract_objects.py:296` `process_video`。映像のライブ転送機能があっても、現行 `offline_mono` は保存動画を入力する。カメラ姿勢の推定から機体の移動までには、さらに尺度・機体との座標対応・経路・制御が必要である。

## 8. 次の授業へ進む確認

まず図を見ながら、「初期地図がないとき」「順調に追跡しているとき」「追跡を見失ったとき」の三つを口頭でたどる。続いて、一枚の画像から特徴、地図との対応、姿勢へ進むデータの変化を説明する。

その後、画像と視線、複数画像による奥行き、地図との照合、誤差を減らす調整の順に理論を学ぶ。現在の不調原因はこの文書では断定しない。全体像がつかめてから、問題の動画・区間・期待する結果を定めて診断する。
